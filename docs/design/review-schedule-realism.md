# 復習予定の現実化（調査と仕様案）

対象: 復習タブの「先の予定」（`TodayPanel` / `App.tsx reviewSchedule`）と FSRS 間隔。
調査日: 2026-09-30（実データ: denken3 / `denken_reviews` 232件・試験 2027-02-06・残129日）。

## 1. 結論

「先の予定が意味をなさない」原因は表示ではなく**間隔の出し方**と**予定の作り方**の2点。

1. **安定度・間隔が検証範囲を大きく超えている。** A→A（2回目が46日後）で次回が**515日後**（試験の1年以上あと）になる。
   実測の最大ギャップは51日で、31日超の観測は43件のみ。しかもその43件の約30%（13件）が C（忘れた）。
   「520日で覚えている」という根拠はデータに一つも無い。
2. **先の予定は「いま入っている due_date の集計」でしかない。** 今日の溜まり（期限超過）が
   消化されたときに発生する再復習、これから着手する未着手の復習は一切入っていない。
   だから「今日」と「○日以降」に偏り、間に何も無いように見える。

一方、期限超過の量は想定（100件近く）より小さい: **31件**（A 19・B 12）。ただし28件は7日以上超過。

## 2. 事実（実データ）

| 項目 | 値 |
|---|---|
| 着手済み（due あり） | 232（S 17 / A 156 / B 52 / C 7） |
| 期限超過＋今日 | 31（うち7日超 28・14日超 24） |
| 今後7日の予定 | 12（約2件/日） |
| 11月 / 12月 / 1月 | 54 / 27 / 54（S の最終確認17含む） |
| 試験日より後 | 15（試験までに一度も復習されない） |
| 安定度の中央値 | A 72日 / B 52日 / C 2日 |
| 最適化パラメータ | v8（510演習・278件で学習。w[3]=13.98、同日項 w[17..19]=0） |
| 直近の演習量 | 9/24 21問37分・9/29 12問26分・9/30 18問96分（新規含む） |
| 演習ギャップ別の忘却（C率） | ≤1日 19% / 2-3日 11% / 4-7日 4% / 8-14日 4% / 15-30日 5% / 31日超 30% |

標準パラメータでも A,A(46日後) は 313日後になる。原因は最適化だけでなく、
A を `Rating.Easy` に写していること（Easy ボーナス）と、低い想起確率での成功が
安定度を大きく押し上げる FSRS の性質にある。最適化パラメータは約1.6倍にする。

## 3. 仕様案

### 3-1. 目標は「試験当日の想起確率」。安定度を検証範囲までしか信用しない

**守るもの**: 全カードについて、試験当日の想起確率 R ≥ 0.90（直前期の目標保持率）。
復習回数は目標ではなく、ここから逆算される結果にすぎない（当初案の「試験前に最低3回」は
この目標と結びつかない代理指標だったため撤回した）。A は1回の自己評価であって状態ではなく、
試験日まで A を保てているかは当日まで観測できない。観測できるのは R だけである。

FSRS は「R が目標保持率を割る前に復習日を置く」ので、S が正しければ目標は満たされる。
ずれているのは **S の信頼性**（§1・§2: 最長ギャップ51日に対し S=236日、31日超の約3割が C）。

- 間隔・予定日の計算に使う S を `S_eff = min(S, CREDIBLE_STABILITY_DAYS)` で頭打ちにする。
  上限は「実測で検証できた最大ギャップ」を超えない定数から始める。実測が貯まったら引き上げる
  （下げる方向の判断は不要＝原則 §0「不確実性はやる側へ」に一致）。
- 試験当日の R（S_eff で評価）が 0.90 を割るカードは、割る前に復習を1回入れる。
  この仕組みは `applyExamHorizon` に既にあり、S_eff を渡すだけでよい。
- 試験前の復習回数はカードごとに変わる（前回が遅く S_eff が大きいカードは 0〜1回）。一律の回数は置かない。
- 既存の直前期テーパー（残28日→14日・残14日→7日）はそのまま重ねる。
- **決定的再生を壊さない**: 頭打ちは定数で、実施日・試験日以外のデータに依存しない。
  履歴の再生結果は何度でも一致する。
- 既存カードは `api/_lib/reschedule.ts` と同じ「再生して upsert」経路で一度だけ引き直す
  （w・保持率は変えない）。マイグレーション不要。
- 定数は実測に合わせて決める: 31〜61日ギャップでの「忘れなかった」割合（実測0.70・n=43）と、
  モデルの R（約0.82）が揃うように。実装時に決め、ここへ追記する。
- 「試験日より後」の15件は、S_eff で試験前へ戻る。

### 3-2. 先の予定を「シミュレーション」にする

新規ファイル `src/lib/reviewForecast.ts`（純関数）と `src/features/questions/ForecastStrip.tsx`。
`TodayPanel` の5行目（日付ストリップ）をこれに差し替える。

入力: 全カードの (due, stability, status)、未着手数、`policy.forwardSlotsToday`、
`estimateMinutes`、処理能力（分/日）。

日ごとのループ（14日先まで）:

1. その日に due なカード＋繰越（バックログ）を密度順に並べ、**能力の範囲で**消化する。
2. 消化したカードは、標準の成功（B 相当）で再スケジュールし、3-1 の S_eff（頭打ち）で future due に積む。
3. 新規着手枠（`forwardSlotsToday`）ぶんの未着手を着手し、`attemptsPerMastery` 回ぶんの
   再復習（1日後・3日後・7日後…の既定系列）を future due に積む。
4. 日ごとに 件数・推定分・繰越を記録する。

**能力は「利用者の実績ペース」ではなく、宣言した時間予算（未選択なら完走に必要な分/日）を使う。**
実績ペースで能力を決めると、停止が続くほど予定が「軽く」見える（`forwardSlotsToday` が
消そうとした挙動の再発）。能力が足りなければ繰越が増えて見える ― それが現実。

表示: 各日「件数・約◯分」と、バックログの**完全消化予定日**（能力どおりに進んだ場合）。
能力超過の日は色を変える。既存の `policy.feasibility`（shortfall）と同じ語彙で出し、
別の警告を増やさない。

### 3-3. 今日の件数について

- 今日のライン（`planToday`）は変えない。期限超過31件は「順番待ち」込みで総量を減らさず、
  密度順に消化する現行の設計で足りる。
- 変えるのは**予定の見せ方**（3-2）と**安定度の頭打ち**（3-1）だけ。

### 3-4. S（復習不要）の廃止【確定】

S は FSRS の更新を止め、試験21日前の最終確認1回に置き換えるだけで、最適化の学習にも入っていない
（17件）。「復習不要」は自己申告で、安定度の過大評価と同じ問題を別の形で持ち込む。廃止し、既存の S は
A として FSRS の追跡に戻す（S の解答時間の中央値は60秒＝速いので、3-5 の規則では Easy になる）。
`finalCheckDue` と S 専用の分岐（`calcFSRS` の早期リターン・UI のボタン）は削除する。

### 3-5. 解答時間を評価（Rating）に反映する【案】

現状、解答時間は FSRS に入っていない（評価は A→Easy / B→Good / C→Again の固定。最適化の学習データも
評価と経過日数のみ）。時間の使い道は、見積もり・今日のラインの並び・分析タブの4象限だけ。

使う基準は **本番の持ち時間 E**（A問題5分・B問題10分・`examTime.ts`）。学習中の切り上げ時間
（`cutoffSeconds` ＝ min(典型×1.5, E)）は使わない。切り上げは「これ以上粘らない」アラームで、
従うと記録時間が縮み、縮んだ実測が次の切り上げを縮める自己参照（ラチェット）になると
`solveTimer.ts` 自身が書いている。E は固定値なので自己参照にならず、データにも依存しない。

| 自己評価 | 解答時間 t | FSRS Rating | 意味 |
|---|---|---|---|
| A | t ≤ 0.5E | Easy | 本番で余裕を持って解ける |
| A | 0.5E < t ≤ E | Good | 解けるが時間に余裕が少ない |
| A | t > E | Hard | 正答でも本番では時間切れ（失点） |
| B | 任意 | Hard | 方向性のみ。本番では0点（`STATUS_PROB` の置き方と一致） |
| C | 任意 | Again | 変更なし |
| 計測なし | - | 現行の写像のうち**Easy→Good** | 時間で Easy を裏付けられない |

- **下げる方向にだけ使う。** 時間が速いことを理由に現行（Easy）より長い間隔は作らない。
  不確実性は「やる側」へ倒す（原則 §0）。
- **E の見直しが先に要る。** 現行は A問題14×5分＋B問題3×10分＝100分で、90分の試験時間を超える。
  「逆算」なら、見直し10分を残して 80÷(14＋3×2)＝**A 4分・B 8分**、見直しなしで A 4.5分・B 9分。
  `examTime.ts` の定数を先にこの値へ直す（分析タブの「遅い」判定も同じ値を使うため連動する）。
- **決定的再生**: t と E（問題のタイトルから決まる）は履歴から再現できるが、`deriveFromHistory` は
  履歴しか見ないので、記録時に Rating を履歴エントリへ書き残す（`policy` と同じ扱い）。既存の
  履歴は一度だけ t と現行の E から Rating を埋め戻す。
- **最適化も同じ写像で学習し直す。** 現行の学習データには Hard が0件（`trainSet.ts`）で、Hard に
  対応する重みは一度も調整されていない。写像を変えた時点で学習データも作り直し、再学習する。
- **リスク**: タイマーは中断・放置に弱い（記録時に中央値×3または15分で捨てる）。計測なし35%の
  扱いが上の最終行。この規則は「時間と将来の忘れにくさの関係」が未検証なので、最適化の対数損失が
  改善するか（0.268）を確認してから採用する。

## 4. 検討したが採らなかった案

- **間隔の一律上限（45日）や「試験前に最低N回」**: 目標（試験当日の R）と結びつかず、
  S が十分信頼できるカードにも回数を強いる。
- **表示期間を伸ばす（8日→30日）**: 予定が「10/17に8件」のような塊のままで、未着手・再復習が
  入らない問題が残る。
- **A を Good に写す**: Easy ボーナスは減るが、頭打ちが無ければ 46日ギャップ後の安定度は
  なお過大。S の頭打ち（3-1）で足りるため、評価の意味（A=見ずに解けた）は変えない。
- **最適化パラメータを捨てる**: log_loss は 0.314→0.268 と改善しており、短い間隔の
  予測は有効。問題は未観測領域への外挿だけなので、範囲を区切る（3-1）。
