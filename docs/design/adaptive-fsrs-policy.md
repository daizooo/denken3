## 2. 実データから判明した事実 ―― 危機感の方向が実態とずれている

### 2.1 【重要】合格ラインに対しては、大幅に先行している

現行モデルで想定得点を手計算すると:

```
想定得点 = [ (179+17)×0.92 + 36×0.60 + 208×0.20 ] ÷ 440 × 100
        = [ 180.32 + 21.60 + 41.60 ] ÷ 440 × 100 = 55.3 →  55点
目標点   = 60 + 10 = 70点        不足 15点

1問を未着手→A へ上げたときの伸び = (0.92 − 0.20) ÷ 440 × 100 = 0.164点
必要問数 requiredQ = 15 ÷ 0.164 ≒ 92問
必要ペース = 92問 ÷ 87日 = 1.06 問/日
```

**目標日まで 1日1問で足りる。** 実績は 7/17〜8/20 の35日間で修得（A以上への到達）304回＝
平均 8.7問/日。14日停止で EWMA が半減しても 3〜4問/日 で、**必要ペースの3〜4倍**。

時間に換算すると:

```
未着手 92問 × 約6.7分            ≒ 10.3時間
due   106問 × 約3分（復習は初見の半分） ≒  5.3時間
合計 15.6時間 ÷ 87日 =  1日あたり 約11分
```

**「合格ライン＋10点」を守るのに必要なのは、1日約11分。** 育児中でも成立する数字であり、
目標を下げる必要は現時点でまったく無い。要求3（合格ラインは厳守）は、**現状のデータでは
何も犠牲にせずに満たせる**。

### 2.2 【最大の問題】復帰した日に「今日36問・約4時間」の崖が立つ

`planDailyReviews()` の推奨ラインは

```
recommendedCount = min(due総数, max(urgentCount, ceil(due総数 ÷ catchUpDays), 1))
catchUpDays = 3（試験まで87日あるため）
→ ceil(106 ÷ 3) = 36問  → 実測時間で 約4時間
```

**この式には「その人が今日どれだけ時間を使えるか」が一切入っていない。** 締切からの逆算だけで
決まる。14日休んで復帰した日に「今日36問・約4時間」と出れば、育児中には確実に折れる。

しかも §2.1 のとおり、合格に必要なのは 1日1問・11分である。**アプリは、合格に不要な負荷で
利用者を潰す構造になっている。** これが自動最適化で最初に直すべき点。

### 2.3 【検証の空白】想定得点55点は、一度も検証されていない

- `denken_mock_sessions` が **0件** ＝ CBT 実測がなく、`ScoreEstimate.actual` / `gap` が常に null
- 理解度 **C が1件も無い**（A:179 / B:36 / S:17 / C:0）。「答えを見た」を一度も記録していない
- 平均 difficulty が **2.53** と低い ＝ `RATING_MAP` で A→`Easy` が179回流れ、FSRS が
  「この人にとって簡単」と学習し続けている

`STATUS_PROB.A = 0.92` は「Aを付けた問題は本番で92%正解できる」という仮定だが、
**その A 自体が「解答を見た後の自己申告」である**（Phase 1 の設計書 §1.2①）。
C が0件という分布は、自己評価が甘い側に寄っている可能性を示す。55点は上振れしている恐れがあり、
**この不確実性こそが「合格を確実にする」ことへの最大のリスク**である。

### 2.4 【バグ】S の17問が、試験前最終確認から永久に漏れている

`fsrs.ts` の `finalCheckDue()`（§6-4・課題4）は、S にした問題を試験21日前＝**2027-01-16** に
一度だけ復習キューへ戻す仕様。しかし実データでは **S:17問すべてが `due_date IS NULL`**。

原因: この17問は 2026-07-26（15問）と 2026-08-11（2問）に記録されており、
`finalCheckDue` の実装（Phase D・2026-09-01）**より前**。当時の S は due_date=null を書いていた。
`deriveFromHistory` は次に記録したときに再導出して直すが、**S は due_date=null のため
復習キューに出てこない → 記録される機会が来ない → 永久に直らない**（デッドロック）。

影響: 最も確実な得点源17問が、試験直前に一度も確認されない。**要求3（合格を確実に）に直接反する。**

修正は一度きりのバックフィル1行で済む（§5 Phase 0）。

## 3. 自動最適化の設計

### 3.1 現行の推奨ノルマが持つ構造的欠陥

```ts
recommendedNorm = max(1, ceil(clamp(requiredPace, currentPace×0.8, currentPace×1.3)))
```

**現在ペースが下がるとノルマも下がる。** 育児で停止が続けば `currentPace → 0` となり、
上限 `currentPace×1.3 → 0` に張り付いて推奨は `max(1, …) = 1問`。
**「勉強できないから要求を下げる」という、利用者が明確に禁止した挙動そのもの。**

同時に `verdict = 'behind'` が出続け、毎日「遅れている」と言われる（課題2 で既出）。
つまり現行は「要求は下げるのに、判定は責める」という最悪の組み合わせになっている。

### 3.2 正しい分離 ―― 「目標」は下げない、「今日の範囲」は絞る

物理的に、供給（時間）< 必要（学習量）のとき、動かせるものは4つしかない:

| 選択肢 | 本設計での扱い |
|---|---|
| ① 目標得点を下げる | **禁止**（要求3） |
| ② 期日を延ばす | 試験日は動かせない。ただし**科目合格制があり「今回は理論だけ確実に」は正当な戦略**。判断材料は出すが自動では動かさない |
| ③ 範囲を絞る | **自動化する**（コア集合／バッファ集合の分離） |
| ④ 効率を上げる | **自動化する**（保持率の問題別最適化） |

したがって自動最適化の本体は ③ と ④ である。**ノルマではなく、キューの中身を差し替える。**

### 3.3 三層のポリシー

毎日1回、純関数 `optimizePolicy()` が以下を算出する。

```ts
// src/lib/policy.ts（新規）
export interface Policy {
  passMargin: number            // 層1: 動的な安全マージン（点）
  coreIds: Set<string>          // 層2: 合格に必要な最小集合（コア）
  retentionOf(id: string): number // 層3: 問題ごとの目標保持率
  dailyFloor: number            // 停止中でも切らない最低ライン（問）
  feasibility: Feasibility      // 供給 vs 必要 の実現可能性
}
```

#### 層1: 安全マージンを、推定誤差から自動で決める

現行は `DEFAULT_PASS_MARGIN = 10` 固定。「合格を確実に」するなら、**推定が信用できないほど
マージンを厚くする**のが正しい。

```ts
// CBT実測が無い間は最大マージン。実測が増えるほど、実測とのズレの大きさで決める。
function passMargin(est: ScoreEstimate, sessions: MockSession[]): number {
  const finished = sessions.filter(s => s.status === 'finished' && s.score != null)
  if (finished.length === 0) return 15          // 未検証 → 厚く（現行10より保守的）
  const bias = mean(finished.map(s => est.estimate - s.score!))  // 正 = 想定が甘い
  return clamp(8 + Math.max(0, bias), 8, 20)    // 甘い分だけ上乗せ
}
```

現状（実測0件）では **マージン15点＝目標75点**。requiredQ は 92問 → 約123問へ増える
（必要ペース 1.4問/日）。**目標を上げる方向に自動で動く**のが要求3に沿う。
CBT を受けて想定が正しいと分かれば自動で 8点まで下がり、無駄な負荷が消える。

#### 層2: コア集合とバッファ集合を分ける

`passTarget.planPassTarget()` は既に「目標到達に必要な最小の問題集合」の**問数**を返している。
これを**問題IDの集合**まで返すよう拡張する（伸びの降順に積む処理は既にある。返り値に
`coreIds` を足すだけ）。

| 集合 | 定義 | 扱い |
|---|---|---|
| **コア** | 合格点＋マージンに到達するのに必要な最小集合（現状 約123問） | 保持率を高く保つ。時間が無い日はここだけ出す。**絶対に切らない** |
| **バッファ** | それ以外 | 保持率を下げてよい。時間が無い日は後回し（実質切り捨て） |

**これが「設定を下げずに範囲を絞る」の実装。** 1日5分しかない日でも、その5分は合格に
最も効く5分になる。

#### 層3: 保持率を問題ごとに決める

現行 `retentionFor(eventDate, examDate)` は日付だけを見る単一のグローバル値。これを拡張する。

```ts
function retentionOf(id: string, mode: EstimateModeKey, policy: Policy, date, examDate): number {
  const base = policy.coreIds.has(id)
    ? 0.90                                    // コア: 落とさない
    : (mode === 'calc' ? 0.85 : 0.80)         // バッファ: 回転優先
  return diffDays(date, examDate) <= 60 ? Math.max(base, 0.90) : base
}
```

計算/暗記の分離（Phase 1 設計書 §4.2）は、この式に吸収される。
**総復習量が増えないよう、コアを上げた分はバッファを下げて相殺する**（§6 で実測検証）。

### 3.4 【最重要】決定的再生を壊さないための仕組み

`fsrs.ts` には明示的な制約がある:

> retention を「その実施日から試験日までの残日数」だけで決めるのが要点で、こうすると
> `deriveFromHistory` が `review_history` を再生するたびに同じ結果になる（決定的）。

**ポリシーが日々変わると、この決定性が壊れる。** 過去の予定日が毎日書き換わり、
何が起きているか誰にも分からなくなる ―― まさに利用者が困っている「現状が分からない」状態の悪化。

解決: **その日に適用したポリシーを、履歴エントリに書き残す。**

```ts
export interface ReviewHistoryEntry {
  date: string
  status: Status
  prev?: ReviewSnapshot
  duration_seconds?: number
  attempt?: Attempt                  // Phase 1（解答前コミット）
  policy?: { retention: number }     // ← 追加。記録時に実際に使った目標保持率
}
```

再生時は `entry.policy?.retention ?? retentionFor(entry.date, examDate)` とする。
**旧データは従来式にフォールバックするので後方互換が完全に保たれ、新データは記録時の値で
再生されるので決定的性も保たれる。** Phase 1 の `attempt` と同じ JSONB の器に入るため、
**マイグレーションは不要。**

### 3.5 停止期間の扱い ―― 下げるのではなく、絞る

```ts
// 今日の推奨ラインを、締切だけでなく「使える時間」と「コア集合」から決める。
export function planToday(candidates, policy, budgetMinutes, stats): TodayPlan {
  const core = candidates.filter(c => policy.coreIds.has(c.question.id))
  const buffer = candidates.filter(c => !policy.coreIds.has(c.question.id))
  // ① コアの高リスク分は、予算を超えても必ず線の上に置く（切らない）
  // ② 残った予算をコアの残り → バッファ の順に埋める
  // ③ 予算が未設定・ゼロでも dailyFloor（1〜3問）は必ず出す
}
```

| 状況 | 現行の挙動 | 改訂後 |
|---|---|---|
| 14日停止から復帰 | 「今日36問・約4時間」 | 「今日 **コア3問・約18分**」＋「バッファ103問は順番待ち」 |
| ペースが落ちた | **ノルマが自動的に下がる**（禁止事項） | ノルマは下げない。**バッファが後ろへ流れるだけ** |
| 判定 | 毎日 `behind` | コア基準で判定。現状は `ahead` |
| 5分しかない日 | 予算で上から36問を切る | **コアの最高リスク1問**を出す |

### 3.6 実現可能性は「下げる」のではなく「事実として突きつける」

コアだけでも供給が足りなくなったときは、**黙って目標を下げてはならない**。
`Feasibility` を計算して事実を提示する:

```ts
export interface Feasibility {
  requiredMinutesPerDay: number   // コア完遂に必要な 分/日
  availableMinutesPerDay: number  // 直近の実績から推定した 分/日（EWMA）
  verdict: 'safe' | 'tight' | 'shortfall'
  // shortfall のとき提示する選択肢（自動では選ばない）
  options: ('increase_time' | 'defer_exam' | 'accept_risk')[]
}
```

現状は `requiredMinutesPerDay ≒ 11分` に対し、実績（停止前）は数十分〜数時間。**`safe`**。
`shortfall` になって初めて「次回試験へ回す」等を**利用者に選ばせる**。
アプリが勝手に目標を下げることはしない。

## 4. ts-fsrs の重み `w[]` 最適化を、今はやらない理由

「FSRS の最適化」といえば通常は `w[]`（17パラメータ）のフィッティングを指すが、
**現時点では実施すべきでない。** 根拠は3つ、いずれも実データによる。

1. **母数が足りない。** 総演習 **526回**。FSRS プロジェクトの一般的な目安は
   最適化に 1,000件以上、安定させるには数千件。526件では過学習になる
2. **入力の情報量が無い。** Rating は実質 `Easy`(A:179) と `Good`(B:36) の2値。
   **C が0件で `Again` がほぼ流れておらず、`Hard` は `RATING_MAP` に存在しない。**
   忘却曲線の当てはめは「失敗した記録」から情報を得るので、失敗がほぼ無いデータで
   フィッティングしても意味のある `w` は出ない
3. **入力の妥当性が未検証。** Rating の元である A/B は解答を見た後の自己申告で、
   客観的な正誤データが1件も無い（Phase 1 設計書 §1.2①）。**間違った入力で最適化すれば、
   間違いが固定される。**

`ts-fsrs@5.4.1` はスケジューラであり、`w[]` の最適化器は同梱していない
（別パッケージ `fsrs-rs-nodejs` 等が必要）。**インストール済みの版で最適化APIの有無を
実装前に確認すること。**

**正しい順序**: Phase 1 で客観的な正誤を貯める → `Rating.Hard` と `Again` を実際に流す
→ 演習1,000件を超える → そこで初めて `w[]` 最適化を検討する。
それまでは §3 の「入力パラメータの自動最適化」で十分に効果が出る。

```sql
-- 試験21日前（2027-02-06 − 21日）へ一度だけ戻す。
UPDATE denken_reviews r
SET due_date = p.exam_date - 21
FROM denken_exam_plans p
WHERE r.user_id = p.user_id AND r.exam_id = p.exam_id
  AND r.status = 'S' AND r.due_date IS NULL
  AND p.exam_date - 21 > CURRENT_DATE;
```

併せてアプリ側にも再発防止を入れる（試験日を設定・変更したとき、S の due を計算し直す）。

## 6. 批判的検証

| 論点 | 検証 | 結論・打ち手 |
|---|---|---|
| **そもそも危機なのか** | 実データでは合格ラインに対し必要ペースの3〜4倍で先行。必要なのは1日約11分 | **現時点で危機ではない。** 目標を下げる必要も無い。要求3は無償で満たせる。ただし §2.3 の未検証リスクが残るため、マージンを厚くして吸収する |
| 自動最適化は「勝手に動く」ぶん、現状がさらに見えなくなるのでは | **正当な懸念。** 利用者の一次不満は「現状が分からない」ことであり、自動化はそれを悪化させ得る | だから **Phase A（可視化）を Phase C（自動化）より先に置いた。** 画面に出ていない値は自動で動かさない |
| ポリシーを日々変えると `deriveFromHistory` の決定性が壊れる | 現行コードが明示的に守っている最重要の性質 | `entry.policy` に記録して再生時に使う（§3.4）。旧データは従来式へフォールバック。**この仕組み無しに層3を実装してはならない** |
| コア集合が毎日入れ替わって落ち着かないのでは | requiredQ は想定得点に依存し、A が増えるたびに縮む。境界の問題が出たり入ったりし得る | コア集合に**ヒステリシス**を入れる（一度コアに入った問題は、目標を10%超過して余裕が出るまで外さない）。実装は `policy.ts` 内に閉じる |
| マージンを15点に上げると、要求される問数が92→123問へ増える | 負荷は増える | それでも必要ペースは 1.4問/日・1日約15分で、実績の範囲内。**「確実に合格」を優先する要求3に沿った増やし方**であり、下げる方向の妥協ではない |
| バッファを実質切り捨てるのは、満点狙いを放棄することでは | そのとおり | 現行も `pass` 達成後に `mastery` へ自動昇格する設計になっている。**コアを固めたら自動でバッファがコアに繰り上がる**ので、時間があれば結果的に全問へ向かう |
| `STATUS_PROB.A = 0.92` の妥当性が未検証のまま全計算の土台になっている | **最大の弱点。** 想定得点55点も requiredQ 92問も、この1つの仮定に乗っている | 実測で較正するしかない。**CBT模試を1回受けることが、どの自動最適化よりも価値が高い**（§7） |
| C が0件なのは自己評価が甘いからでは | 断定はできない（実際に「答えを見る前に解けている」可能性もある） | Phase 1 の選択肢コミットで客観データが取れれば判別できる。**それまで `STATUS_PROB` は触らない**（推測で定数を動かすのは、まさに今回やめたい行為） |

## 7. 結論 ―― 次にやるべきことの順序

実データを踏まえると、優先順位は以下になる。

1. **Phase 0（S の17問バックフィル）** ―― 単独で即マージ。合格の確実性に直接効く既知の欠損
2. **CBT模試を1回受ける** ―― コードではなく運用。`denken_mock_sessions` が0件である限り、
   想定得点55点も、必要問数92問も、マージン10点も、**すべて未検証の仮定の上に乗っている**。
   1回の実測が、どの自動最適化よりも精度を上げる
3. **Phase A（可視化）** ―― 「現状が分からない」への直接の回答。自動で動かす前に見えるようにする
4. **Phase B（今日のラインを容量ベースへ）** ―― 復帰時の「36問・4時間」の崖を消す。体感が最も変わる
5. **Phase 1（解答前コミット / 別設計書）と Phase C（保持率の自動最適化）** ―― 並行可
6. **Phase D（`w[]` 最適化）** ―― 演習1,000件超・Rating 4値が流れてから

**要求3への回答**: 合格ライン＋α は、現状のデータでは 1日約11分（マージン15点でも約15分）で
守れる。したがって「勉強できない日が続く」ことへの正しい対処は、目標を下げることでも
ノルマを下げることでもなく、**その日の限られた時間をコア集合へ集中させること**である。
本設計の層2（コア/バッファ分離）と Phase B がそれを実装する。
