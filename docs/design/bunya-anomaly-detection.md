# 分野別 見開き画像の変則検出（PR#101 の続き）

`docs/problem-data-integration.md` が分野別（オーム社 過去問・見開きスキャン）の取り込み設計、
`docs/data-correction-workflow.md` がその運用。本書はそのうち **取り込み時に残っている
Vision コストを削る**ための検討と、その実装（`scripts/detect-bunya-layout.mjs`）の設計を扱う。

## 0. なぜ今これを見るか

PR#101（`scripts/detect-mask-pcts.mjs`）で **年度別**ペーパーのマスク座標は機械測定になり、
Claude の役割は「実行して ok 以外を確認する」に縮んだ。残っている Vision コストは **分野別**の側で、
`docs/problem-data-integration.md` §5 の手順1がそれにあたる。

> 1. **マッピング生成**：サブエージェントが章フォルダの全画像を「左列全高で全ヘッダー走査」して …
>    変則（2問同居・またがり・B問題）に該当する画像は**見開き全体を目視**して … 確定する

つまり章を1つ足すたびに **20〜82枚の見開きを丸ごと読む**。年度別（1回18枚前後）より1桁重い。

## 1. 実績データが示す「変則の量」

収録済み9章のマッピング（`src/data/*Assets.ts`）と §5.1 の実読枚数から集計した。
**非標準**＝2問同居／またがり／`answerXPct`・`answerYPct`・`answerRightYPct`・`regionYPct` の
いずれかを既定値から動かした画像。

| 章 | 実読枚数 | 登録画像 | 非標準 | 標準 | 目視が要る割合 |
|---|---|---|---|---|---|
| dc | 73 | 70（捨て問3） | 6 | 64 | 12% |
| ac1 | 71 | 68（捨て問3） | 3 | 65 | 8% |
| ac3 | 30 | 26（捨て問4） | 8 | 18 | 40% |
| trans | 20 | 15（捨て問5） | 3 | 12 | 40% |
| elec | 79 | 74（捨て問5） | 16 | 58 | 27% |
| mag | 56 | 54（捨て問2） | 3 | 51 | 9% |
| meas | 59 | 50（捨て問9） | 7 | 43 | 27% |
| etheory | 50 | 46（捨て問4） | 4 | 42 | 16% |
| ecircuit | 82 | 69（捨て問13） | 17 | 52 | 37% |
| **計** | **520** | **472**（捨て問48） | **67** | **405** | **22%** |

**520枚のうち405枚（78%）は「1画像＝1問・左＝問題／右＝解答」の既定値どおり**で、
目で見ても何も新しい情報が出ない。ここを機械が「標準」と言い切れれば、実読は原理的に
**520枚 → 115枚（22%）** まで落ちる。逆にいえば、このツールの価値は変則を見つけることではなく
**標準を標準と確定して目視の対象から外すこと**にある。

## 2. 何を手掛かりにできるか

見開きの版面は章をまたいで共通（左ページ左上に「問N 表題 出典コード」、右ページに「解答」「解説」）。
そこで次の手掛かりが使える。左の3つは**版面の幾何**なので、表題のOCRが崩れても効く。

| 手掛かり | 取り方 | 何が分かるか |
|---|---|---|
| 綴じ目 | 語の外接矩形がまったく無い縦帯（中央35〜65%で最大幅） | `answer_x_pct=50` という前提そのものの検算。ずれたスキャンを名指しできる |
| 問ヘッダの数 | 左ページで行頭が「問＋数字」の行 | 0個＝**解答またがり**（前画像の続き）／2個以上＝**2問同居** |
| 解答見出しの位置 | 行頭が「解答」「解説」の行のページ内座標 | 右ページ上端＝標準／右ページ途中＝**`answer_right_y_pct`**／左ページ＝**`answer_y_pct`**／無し＝**丸ごと問題**（`answer_x_pct=100`） |
| 出典コード | `H26-B17` `R1-A15` 形式（英数字＝OCRの信頼度が高い） | 問ヘッダの裏取り |
| 問番号 vs MASTER | `src/data/denken3/riron/ohmsha-bunya/{章}.ts` の `id` 一覧 | **捨て問候補**（登録しない画像） |

`docs/problem-data-integration.md` §2.3・§4.1 が定義する変則3類型＋マスク変則が、
これで全部いずれかの手掛かりに対応づく。**新しい種類の変則を発明していない**——
既に実データで確認済みの型だけを対象にしている。

## 3. 設計方針：測定ではなくトリアージ

年度別（`detect-pcts`）との決定的な違いは、**分野別の変則は行の増減を伴う**ことにある。
2問同居は1画像に2行、またがりは同じ `question_id` に2行。座標1列の UPDATE で閉じない。

そのため本ツールは次を**やらない**。

- **値を確定しない。** `regionYPct` 等は出すが、判定は `check` のまま据え置く。
  「値が出た＝確定」と読まれた時点で、目視の代わりに機械が値を決めていることになる。
- **`--sql` を出さない。** `detect-pcts` が UPDATE 文を出せるのは数値1列の更新だからで、
  こちらは INSERT/DELETE を伴う。誤検出がそのままDBの構造を壊す経路を作らない。
- **未検出を既定値で埋めない。** 読めなかった画像は `miss` として名指しし、値を出さない
  （PR#101 の「miss の列は SQL にも出力しない」と同じ考え方）。

やることは1つだけ：**目視すべき画像を名指しし、それ以外を「見なくてよい」と言い切る。**
`docs/data-correction-workflow.md` §4「抜き取り確認を許容する」の適用範囲を、
年度別から分野別へ広げるということ。

## 4. 実装（`npm run detect-layout`）

```bash
# 取り込み済みの章（Supabaseから直接読む。Google Driveへ戻らない＝workflow §2）
npm run detect-layout -- --chapter elec

# 未取り込みの章（手元の画像。取り込み前のマッピング作成用）
npm run detect-layout -- --chapter elec ./elec/*.png --map
```

判定は3段階で、`ok` 以外だけ `npm run peek` で現物を開く。

| 判定 | 意味 | 目視 |
|---|---|---|
| `ok` | 標準見開き。綴じ目も中央、問ヘッダ1つ、右ページ上端から解答 | 不要（抜き取りのみ） |
| `check` | 変則候補（2問同居・またがり・丸ごと問題・途中から解答・左下から解答・捨て問候補） | **必要** |
| `miss` | 構造を読めなかった（文字が取れない・綴じ目が無い） | **必要** |

出力は表のほか `--json`（機械可読）と `--map`（`src/data/{章}Assets.ts` の雛形）。
`--map` は捨て問候補を**コメント行として出す**——登録しない画像であることと、
見落として抜けたのではないことを、後から辿れるようにするため。

実装上の勘所を2つ。

1. **行はページをまたいで連結される。** tesseract の行認識は、見開きの左右で行の高さが
   揃っていると1行に繋いでしまう（合成フィクスチャで、左の「問13 …」と右の「解答 (3)」が
   同じ行になった）。これがあると「解答見出しは右ページにあるか」を位置で判定できない。
   そこで**語の外接矩形をページごとに選り分けてから行を組み直す**
   （`scripts/lib/ocr-lines.mjs` の `rowsFromWords`）。語は必ずどちらかのページに収まる。
2. **白紙・向き違いを「またがり」と混同しない。** 問ヘッダが無いことは、またがりの根拠であると同時に
   OCR失敗の症状でもある。語が極端に少ない画像は `unreadable`（`miss`）で打ち切り、
   白紙をアプリへ登録する経路を塞ぐ。

依存は PR#101 で入れた `tesseract.js` + `@tesseract.js-data/jpn` のみで、新規追加は無い。
画像デコーダも入れていない（PNG/JPEG のヘッダから寸法だけ読む）。

> `scripts/lib/ocr-lines.mjs` は新規ファイルで、`scripts/detect-mask-pcts.mjs` は**触っていない**。
> 同等の処理（OCR起動・寸法読み・プロキシヒント・Supabase取得）が2箇所にある状態だが、
> マージ済みPRのファイルを触るとコンフリクトの窓が開くため（`CLAUDE.md`）、
> あちらを次に編集するときに寄せる。

### 実データ検証（7章357枚・2026-08-16）

`SUPABASE_SERVICE_ROLE_KEY` を正しい secret キーに設定し直し、実データでスイープした。
結果は**設計の前提が崩れており、ツールは現状「使い物にならない」**。合成フィクスチャの
9ケースは今も全て通るが、それが実データの版面を代表していなかった。

#### 実行結果

```bash
for ch in dc ac1 ac3 trans elec mag meas etheory ecircuit; do
  NODE_USE_ENV_PROXY=1 npm run detect-layout -- --chapter $ch
done
```

`etheory`・`ecircuit` は `denken_question_assets` に該当行が無く（0件）、この環境の
Supabase にはまだ取り込まれていない（`src/data/{etheory,ecircuit}Assets.ts` はマッピング
ファイルとして存在するが、DBへの反映は別工程）。§1 の表が「収録済み9章」としているのは
ローカルの Assets ファイル基準で、Supabase 側は現時点で7章。7章357枚（画像単位の行数。
2問同居は1画像2行）で実行できた。

| 章 | 枚数 | ok | check | miss | ≠あり | check率 | §1の期待非標準 |
|---|---|---|---|---|---|---|---|
| dc | 70 | 0 | 69 | 1 | 68 | 99% | 6 |
| ac1 | 68 | 0 | 68 | 0 | 67 | 100% | 3 |
| ac3 | 26 | 0 | 25 | 1 | 22 | 96% | 8 |
| trans | 15 | 0 | 15 | 0 | 13 | 100% | 3 |
| elec | 74 | 0 | 72 | 2 | 68 | 97% | 16 |
| mag | 54 | 0 | 54 | 0 | 53 | 100% | 3 |
| meas | 50 | 0 | 49 | 1 | 44 | 98% | 7 |
| **計** | **357** | **0** | **352** | **5** | **335** | **98.6%** | **46** |

§5の3点を測った結果：

1. **`≠`（DB不一致）**：357枚中335枚（94%）。migration `012`（三相交流 問15/20/21/24）・
   `013`（静電気 問13/38/39/45/47/48/49/71）で是正した12問・19画像は、いずれも期待どおり
   `check` に挙がった（`newIMG_0441`〜`newIMG_0219` まで個別に確認済み）。だがこれは
   **目標を達成した結果ではなく、全数が `check` に落ちることの副産物**でしかない
   （下記の根本原因を参照）。
2. **見逃し**：`ok` が**全章で0件**。「標準に非標準が混じる」以前に、標準がひとつも
   `ok` と判定されていない。
3. **過検出**：`check` 率 98.6%（目標22%の**4.5倍**）。目視削減という設計目標
   （§1「520枚 → 115枚」）は実データでは機能していない。

#### 根本原因：見出しの版面が設計の前提と違う

§2 は見出しを「問N 表題 出典コード」（`QUESTION_HEADER = /^[問間冏悶]([0-9]{1,3})/`、
`ANSWER_HEADING = /^(解[答荅签]|解[説説誓]|...)/`）としていたが、**実データはこの形をしていない。**
左ページの見出しバッジは「**章タイトル＋問番号**」（`問` の字を含まない）で、右ページの解答見出しも
「章タイトル＋問番号＋の解答」で始まる。実データの OCR 結果（`scripts/lib/ocr-lines.mjs` の
`rowsFromWords` 出力、`normalize` 後）：

| 画像 | 検出された行（左ページ見出しバッジ） | 検出された行（右ページ解答見出し） |
|---|---|---|
| `dc/newIMG_0283.png`（直流回路1） | `直流回路1抵抗直列回路` | `mo直流回路1の解答導私答え(5)6` |
| `trans/newIMG_0458.png`（過渡現象1） | `過渡現象1アア直列回路` | （同型。個別デバッグ未実施） |
| `elec/newIMG_0145.png`（静電気1） | **（語が1つも検出されず。バッジが白抜き文字＋濃色地の反転配色で、二値化に埋もれた可能性）** | `静電気1の解答答え(3` |

`QUESTION_HEADER` は行頭が「問」「間」「冏」「悶」のいずれかであることを必須にしているため、
「直流回路1」「過渡現象1」「静電気1」のどれにもマッチしない。結果、`analyze()` の分岐
(1)（`headers.length === 0` → `continuation`）に**ほぼ全画像が落ちる**
（357枚中352枚が `kind: 'continuation'`）。`ANSWER_HEADING` も同様に行頭が「解」「答」
「【解」であることを要求しており、「{章タイトル}{N}の解答」にはマッチしない。

`elec/newIMG_0145.png` はさらに一段深刻で、見出しバッジの語そのものが**まったく検出できて
いない**。バッジが白文字／濃色地の反転配色になっている画像があり、既定の二値化前提の
OCR ではコントラストを取りこぼす可能性がある（未確認・要調査）。これは正規表現の修正では
直らない。

`kind: 'continuation'` 以外に落ちた画像は357枚中2枚だけ（`elec/newIMG_0152.png`・
`meas/newIMG_0528.png`）で、いずれも本文中に偶然「問N」相当の文字列が現れたことによる
`whole-question` 判定。`miss`（5枚）は綴じ目も検出できなかった画像で、これも「見出しが
無い」ことの副作用で `continuation` の条件と重なっている。

#### この検証の結論

- **このツールは現状の見出し検出ロジックのままでは分野別9章のどれにも使えない。**
  合成フィクスチャ（Chromium + IPAGothic でこちらが用意した版面）は「問N」前提で作ったため
  全部通ってしまい、実データとの乖離を検証前には検知できなかった。フィクスチャが実データの
  代表になっていなかったのが根本の設計ミス。
- 正規表現を「章タイトル＋数字」にゆるめる対症療法は**今回は行わない**。理由は2つ：
  (a) 9章の章タイトルは OCR で安定して読めていない（`elec` の例のように検出自体に失敗する
  画像がある）ため、タイトル文字列に頼る限りどの章でも同程度に脆い。
  (b) 左マージン条件（`x0 / splitX < 0.35`）は本文1行目の字下げ位置とほぼ重なっており、
  「先頭が漢字+数字」まで正規表現を緩めると本文の偶然の一致を新たに拾う恐れがあり、
  未検証のまま重ねると何を直したのか切り分けられなくなる。
- 見出し検出は**版面の文字列パターンではなく、画像構造（バッジの位置・色、二値化前の
  コントラスト処理）を手掛かりにする再設計が要る**。次の一手（§7）に切り出す。

## 6. 効果と限界

- **効果（見込み・未達成）**：章追加時の実読を 520枚基準で 22% まで落とす、という目標は
  §5 の実データ検証で**達成できていない**（check率98.6%）。見出し検出の再設計が終わるまでは
  効果ゼロ（目視を1枚も減らせない）として扱うこと。
- **限界1**：変則の**判断**は機械化していない。2問同居の分割位置や、右ページのどこから解答かは
  最終的に人（Vision）が決める。ツールは「どの画像を見るか」だけを決める。
- **限界2**：電力・機械・法規の分野別は MASTER 自体が未登録（`docs/problem-data-integration.md` §5.1）。
  §5 で判明したとおり見出し検出の正規表現自体が理論9章の実データにも当たっていないため、
  電力・機械・法規（別シリーズの可能性がある）向けの当て直しは、まず理論9章を直してからになる。
- **限界3**：既に取り込み済みの9章に対する**監査**用途（マスクの誤りを一括して洗い出す）は、
  見出し検出が直れば有効に機能する見込み（migration `012`・`013` の12問19画像は実データでも
  正しく `check` に挙がることを確認済み＝§5）。ただし今は「監査」ではなく「ほぼ全数を人力で
  見る」状態と変わらない。
