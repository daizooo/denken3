# 学習時間が逼迫した状況で合格効率を最大化するための改善設計

作成: 2026-09-01 / 対象: 電験3種・理論（2027年2月受験）

本書は「アプリ全体を調査し、**学習時間が極端に減った前提**で、合格までの効率をさらに
上げられる箇所はどこか」を洗い出した調査記録と改善設計である。実装は本PRのスコープ外
（§6 の未決事項に回答が出てから、Phase ごとに別PRで行う）。

---

## 1. 背景 — 何が変わったか

`docs/design/expansion-design.md` §7.2 は、既に「産後1年程度は学習キャパシティが不確定」
という前提を織り込んで設計されている（事前宣言型の休止期間を廃止し、EWMA による適応推定へ）。
その判断は正しく、**時間が減ること自体には既に強い設計**になっている。

しかし実際に子どもが生まれ、学習時間が「減った」だけでなく「**細切れ・不規則・予測不能**」に
なったことで、別の種類のズレが表面化する。

| 変化 | 既存設計が想定していたこと | 実際に起きること |
|---|---|---|
| 総量が減る | EWMA が自動追従する ✅ | 対応できている |
| **1回の長さが読めない**（5分／30分／ゼロ） | 未対応 | 「今日の推奨7問」が実時間で何分か分からない |
| **開いてから決める時間がない** | 未対応 | タブ移動・絞り込みの操作自体が隙間時間を食う |
| **中断が常態**（片手・抱っこ・寝かしつけ） | 一部対応（タイマーの pause） | 記録までのタップ数・オフラインが効く |
| 目標水準 | 「全問A以上」＝ 440問 | 合格（60点）に必要な水準と乖離し、常時「遅延」判定 |

**本書の中心的な主張は1つ**: 現行アプリの計画単位はすべて「**問題数**」であり、
逼迫しているのは「**分**」である。この単位のズレが、以降に挙げるほとんどの課題の根にある。

## 2. 現状の到達点 — 改善不要と確認した点

調査の結果、以下は既に十分よくできており、**触らない**ほうがよいと判断した。

1. **ペースの適応推定（EWMA・半減期14日）** — `src/lib/pace.ts`。
   事前にキャパシティを宣言させない設計は、育児下の前提として明確に正しい。休んだ日も0問として
   算入されるため、休止が自動的に織り込まれる。
2. **「上限で切らず、線を引く」復習UI** — `planDailyReviews` の推奨ラインと
   「以降は順番待ち（遅れではありません）」の文言。罪悪感を出さない設計として妥当。
3. **遅延を赤字で出さない** — `QuestionCard` は「N日遅延」ではなく忘却リスク帯
   （優先／そろそろ／余裕あり）で表示する。FSRS が経過を織り込む以上これが正しい。
4. **FSRS の試験日クリップ＋直前期テーパー** — `clipDueToExam`。試験後に復習が漏れる問題と、
   直前期に間隔が開きすぎる問題の両方を潰しており、追加不要。
5. **履歴からの再導出（`deriveFromHistory`）** — アルゴリズムやパラメータを後から変えても
   `review_history` から全状態を再計算できる。**§3 の課題5（保持率の変更）を安全に試せるのは
   この設計のおかげ**であり、既存設計の最大の美点。
6. **想定得点の出題比率の代理** — `estimateScore` は「オーム社問題集の収録数比」を出題比率の
   代理としているが（設計書 §7.7(4) が「年度別の topic 集計で置き換える」としていた箇所）、
   収録済みの年度別6回分（R5上〜R7下・108問）の `topic` と突き合わせたところ、**実測と
   ほぼ一致していた**。ここは置き換え不要と判断する。

   | 分野 | 収録数比（現行の代理） | 年度別6回の実測（問数ベース） |
   |---|---|---|
   | 電気回路（dc/trans/ac1/ac3） | 174/440 = 39.5% | 45/108 = 41.7% |
   | 電磁気（elec/mag） | 127/440 = 28.9% | 32/108 = 29.6% |
   | 電子理論（etheory/ecircuit） | 94/440 = 21.4% | 21/108 = 19.4% |
   | 電気及び電子計測（meas） | 45/440 = 10.2% | 10/108 = 9.3% |

   （実測はB問題の配点2倍・選択問題の非選択分を補正していない問数ベースの近似。傾向の確認には十分）

## 3. 発見した課題

優先度順。各項に「証拠（コード上の該当箇所）」「帰結」「提案」を書く。

### 3.0 実測データ（2026-09-01 時点・分析タブ「理解度×解答時間」より）

以降の課題の根拠になるので先に置く。ユーザーの実データを分析タブのカードから読み取ったもの。

- 着手済み **232 / 440問**（52.7%）、うち解答時間の計測あり **207問**
- 4象限: A・速い **100** / A・遅い **71** / 誤答・速い **4** / 誤答・遅い **32**
  （A以上は 171/207 = 82.6%）

カードに表示された「中央値比」と実秒数から、**難易度帯ごとの実測中央値を逆算できた**:

| 難易度帯 | 実測中央値 | 逆算の根拠（表示値） |
|---|---|---|
| **1** | **約1.9分**（116秒） | 単相交流 問59: 600秒 ÷ 5.2 = 115秒／問36: 596秒 ÷ 5.1 = 117秒 |
| **2** | **約5.3分**（319秒） | 静電気 問47: 1791秒 ÷ 5.6 = 320秒／問14: 1693秒 ÷ 5.3 = 319秒／三相交流 問14: 1658秒 ÷ 5.2 = 319秒 |
| 3 | 不明 | 該当12問・計測数が少なく安定した中央値が出ない |

逆算に使った5問はいずれも `studyMode: 'calc'`（`elec_47` `elec_14` `ac3_14` は難易度2、
`ac1_59` `ac1_36` は難易度1）。**難易度1と2で 2.8倍の差**があり、difficulty は所要時間の
予測子として十分に機能している（→ 課題10を訂正）。この実測値を提案Aの既定値の根拠にする。

### 課題1【最重要】計画の単位が「問題数」で、「分」ではない

**証拠**
- `planDailyReviews()` の戻り値は `recommendedCount`（問数）。
- `analyzePace()` の `currentPace` / `requiredPace` / `recommendedNorm` はすべて「問／日」。
- 時間（`duration_seconds`）を扱っているのは `analytics.ts` の `quadrantMatrix`（事後分析）だけで、
  **計画側は時間を1秒も見ていない**。
- `reviewValue()` のスコアは `理解度 × 重要度 × (0.15 + 忘却リスク)`。**コスト（所要時間）の項がない**。

**帰結**
- ヘッダの「今日の推奨 7問」が、実時間で10分なのか70分なのか分からない。15分しか取れない日に
  7問は達成不能で、未達が続くと `verdict='behind'` → `needsReplan` → 「遅延が続いています」バナー。
  **時間軸のズレのせいで、適応設計であるはずのペース分析が慢性的な遅延判定を出す。**
- 価値順に並べているため、キューの先頭に「10分かかる計算問題」が来ることがある。5分しかない日に
  開くと、**着手できずに終わる**。時間が希少なときに最適な貪欲順は価値そのものではなく
  「**価値 ÷ 所要時間**」である（1分の暗記問題2問のほうが、10分の計算問題1問より期待得点が高い場面がある）。

**提案A: 所要時間の推定（新規 `src/lib/estimateMinutes.ts`）**

推定の優先順:
1. その問題自身の直近の実測（`review_history` の `duration_seconds`。外れ値は §3 課題13 のとおりクリップする）
2. 同じ `難易度 × studyMode` の実測中央値（難易度別中央値は `quadrantMatrix` が既に算出済み）
3. 既定値（実測が1件も無いときだけ使う）

既定値は 2026-09-01 の実測（§3.0）に合わせて設定する:

| | calc | memory |
|---|---|---|
| 難易度1 | 2分 | 1.5分 |
| 難易度2 | 5.5分 | 2.5分 |
| 難易度3 | 9分 | 3分 |

ステータス係数（未着手・C: 1.0 / B: 0.7 / A: 0.5）は**既定値にのみ**掛ける。実測値には
計測時点のステータスが既に反映されているため、二重に補正しない。見積もりが過大に振れても
「予算に入る問題が減る＝早く終わる」という安全側に倒れるので、精緻な補正は入れない。

データ源は既に完成している（`§7.6` の計測が `duration_seconds` として蓄積中）。新規の計測UIは不要。

**提案B: 時間予算モード（新規 `src/features/questions/TimeBudgetBar.tsx`）**

復習タブ上部に `[5分] [15分] [30分] [指定なし]` のチップを置く。選ぶと、
- キューを「価値 ÷ 推定所要分」の降順に並べ替え、
- 累積推定時間が予算に達したところに線を引く（**現行の推奨ラインの一般化**であり、UIの新概念を増やさない）。

「いま何分ある？」に答えるだけで、その予算で期待得点の伸びが最大になるセットが出る。これが
本書で提案する改善のなかで**最も効果が大きい**。

**提案C: 既存の表示を「分」でも出す**

「今日の推奨 7問（およそ42分）」のように併記する。ペース分析の主要指標にも「現在ペース 12分/日」を追加。

**実装規模とコンフリクト影響**（CLAUDE.md のコンフリクト最小化方針に沿って評価）
- 新規ファイル2つ＋ `reviewPlan.ts` への**関数追加**（既存関数は変更しない）
- `App.tsx` の変更は 20行程度（チップの state と `filteredQuestions` の並び替え差し替え）

### 課題2【重要】目標が「全問A以上（440問）」で、合格に必要な水準と乖離している

**証拠**
- `pace.ts` 冒頭: 「ゴールの定義: 『全問に着手した』ではなく『全問が A 以上』」。
- `remainingQ = 440 - masteredQ`。分母が440問で固定。

**帰結**
理論の合格は60点（18問中おおむね11問正解）。440問すべてA以上は「合格」ではなく「満点狙い」の目標。
時間が潤沢なら健全な目標だが、育児下では**到達不能な目標に対して毎日 behind と判定される**。
`estimateScore()`（想定得点）は既に実装済みなのに、**ペースの目標には接続されていない**のがもったいない。

**提案: 目標モードを2つ持つ**
- `pass`（合格ライン到達・**新設**）: `estimateScore` が `passingScore + マージン`（既定 +10点）に
  届くために必要な最小の問題集合を求め、それを `remainingQ` の分母にする。
  `ChapterImpact.impact`（章を全問A相当にしたときの総得点への寄与）が既にあるので、
  **インパクト降順に積み上げるだけで実装できる**。
- `mastery`（全問A以上・現行）: `pass` を達成したら自動でこちらへ昇格。

**効果**: 「合格まであと◯点／あと◯問」が出る。育児下で最も効く動機づけであり、同時に
`replanOptions` の `narrow`（現状は文章だけで、押せるボタンではない）を実行可能な機能に変える。

### 課題3【重要】新規着手と復習が別画面で、「今日やること」が1画面にまとまっていない

**証拠**
- `App.tsx` の `baseQuestions`: 復習タブは `r.due_date` を持つ問題だけを通す。
  未着手（`due_date=null`）は**復習タブに絶対に出てこない**。
- 一方、新規着手のノルマ（`pace.recommendedNorm`）は**分析タブにしか表示されない**。

**帰結**
5分の隙間にアプリを開いて「今日の復習はありません」と出ても、実際には新規着手を進めるべき日がある。
ユーザーが自分でタブを移動し、絞り込みを開いて未着手を選ぶ必要がある。**隙間時間の相当部分が
「何をやるか決める操作」に消える。**

**提案**: 復習タブを「今日の学習」に一本化する。
1. 復習due（価値順）を先頭に置き、
2. その後ろに新規着手候補（推奨ノルマ数・章の学習順）を同じキューとして継ぎ、
3. 課題1の時間予算の線をキュー**全体**に引く。

新規と復習の区切りは小見出し1行で示すだけでよい（現行の推奨ラインと同じ見た目）。

**併せて修正したい軽微な不整合**
`reviewDueCount()` は今日タブで `r?.status === '未着手'` を件数に含めるが、`baseQuestions` は
未着手を除外する。つまり**章チップの件数と、実際に表示される問題数が食い違う**。
メモだけ保存した問題は `status='未着手'` の行が生成されるため、実際に起こり得る。

### 課題4 S（復習不要）にした問題が、試験まで一度も戻ってこない

**証拠**: `fsrs.ts` — `if (status === 'S') return { due_date: null, last_reviewed: eDate }`。

**帰結**: 時間がないとき「S」を多用するのは合理的な節約行動だが、S にした問題は `due_date=null` の
ため FSRS の忘却追跡から完全に外れ、**試験直前に一度も確認されない問題群**が積み上がる。
9月にSにした問題を2月の本番で落とす、という形で効いてくる。

**提案**: S にも「試験前の最終確認」を1回だけ入れる。`due_date = 試験日 - N日`（既定21日）。
`clipDueToExam` の直前期テーパーと同じ思想の自然な拡張。S の意味を「通常の復習キューから外す」に
留め、「試験前確認からも外す」は別操作（完全除外）として分ける。

### 課題5 FSRS の目標保持率が既定90%のまま — 時間予算に対して復習量が過大

**証拠**: `fsrs.ts` — `new FSRS({ enable_short_term: false })`。`request_retention` が未指定なので既定 0.9。

**分析**: FSRS-5 の想起確率式 `R(t) = (1 + FACTOR·t/S)^DECAY`（`DECAY=-0.5`, `FACTOR=19/81`）から、
同じ安定度 S に対する次回間隔は `t = S·(81/19)·(R⁻² − 1)`。

| request_retention | 間隔（Sを1としたとき） | 復習の発生頻度 |
|---|---|---|
| 0.90（現行の既定） | 1.00 | 基準 |
| 0.85 | 1.64 | −39% |
| 0.80 | 2.40 | −58% |

**1回勝負・試験日固定・学習時間が希少**という条件では、0.9 は保守的すぎる可能性が高い。
保持率を下げると1問あたりの想起確率は下がるが、**同じ時間で触れる問題数が増える**ため、
未着手を減らす効果のほうが大きい局面がある（特に現在のように未修得が多い段階）。

**提案**: `request_retention` を設定可能にし、既定 0.85、試験60日前から 0.9 へ戻す（直前期は精度優先）。

**注意**
- これは学習方針の根幹に触れるため **§6 の未決事項としてユーザー判断を仰ぐ**。
- 変更しても `deriveFromHistory` が `review_history` から全状態を再計算するため、過去データは壊れない。
- 上表は FSRS-5 標準の定数に基づく試算。採用前に、インストール済み `ts-fsrs@5` の実装で
  数問ぶん実測して確認すること。

### 課題6 年度別↔分野別のリンクが全件未設定で、誤答の前倒し復習が動いていない

**証拠**
- `boostReview()`（年度別で誤答した問題に対応する分野別問題の `due_date` を今日にする）は
  `App.tsx` に実装済みで、`MockExamView` に `onBoostReview` として渡されている。
- しかし `PaperQuestion.sourceQuestionId` は、収録済み6回分108問すべてで**未設定**
  （`_skeleton.ts` のコメント1件を除き0件）。つまり**この機能は一度も発火しない**。

**提案**: 手入力せず、ビルド時に自動リンクする。
分野別のタイトルには出典が入っている（例: `抵抗直並列回路（H16-A4/R6下-A7）`）。
`R6下-A7` → ペーパー問題 `r6-2_a07` へ機械的に解決できる。新規 `src/lib/sourceLink.ts`（純関数）を
追加し、`papers/index.ts` の既存ビルド時チェック（`validatePaper`）に相乗りさせる。

**実現可能性の実測**: 分野別タイトル中の `R5上`〜`R7下` の出典は **57件**。収録済み108問の
**約53%** を手入力ゼロで自動リンクできる。

**制約（先に埋めるべきデータの穴）**: 出典がタイトルに入っていない章がある。

| 章 | 収録数 | タイトル中の出典数 |
|---|---|---|
| 静電気（elec） | 72 | **0** |
| 三相交流（ac3） | 22 | **0** |
| 電気計測（meas） | 45 | **3** |
| （他6章） | 301 | 359 |

この3章（139問）はリンク不可。自動リンクの前に**タイトルへの出典補記**が要る（データ作業として別PR）。

### 課題7 オフラインで使えない／ホーム画面アプリとして起動しない

**証拠**
- service worker が存在しない（`src/`・`public/`・`index.html` に該当なし）。
- `public/manifest.webmanifest` の `"display": "browser"`。
- 問題画像は Supabase の非公開バケットの署名URL（TTL 3600秒）で毎回取得している。

**帰結**: 抱っこ中・寝かしつけ中・移動中など、**電波が弱く読み込み待ちが許されない場面こそが
隙間時間**である。今は起動のたびにネットワーク往復が要る。

**提案（段階的・後半ほど重い）**
- a) `"display": "standalone"` にする（**1行**。ホーム画面から即起動しブラウザUIが消える）
- b) アプリシェル（HTML/JS/CSS）を service worker でキャッシュ → 起動が即時になる
- c) 「今日の分」の問題画像を先読みして Cache Storage に置く（署名URLのTTLとの整合が要検討）
- d) 記録のオフラインキュー（IndexedDB）→ 復帰時に upsert。現行の「最後の書き込みが勝つ」方針と相性が良い

a) は単独で即実施可能。b)〜d) は独立したPRにする。

### 課題8 記録までの導線が1タップ多い

**証拠**: `ProblemViewer` に記録ボタンがない。「問題を解く」→ 解く → 閉じる → カードを探して A/B/C、
という往復になる。

**帰結**: 片手操作・いつ中断されるか分からない前提だと、この1タップと「カードを探し直す」視線移動が効く。
中断されて記録し損ねると、タイマーは日跨ぎで破棄され（`timer.ts`）、計測データも失われる。

**提案**: `ProblemViewer` の「解答を見る」の隣に A/B/C/S を置き、押したらそのまま閉じる
（解答時間の確定も同時）。既存の `updateStatus` をコールバックとして渡すだけで、ロジックの追加はない。

### 課題9 分析タブは「読む」設計で、隙間時間には重い

現在の分析タブは、ペース分析・弱点ランキング・学習曲線・4象限・想定得点・章別進捗と密度が高い。
情報としては良質だが、5分の隙間に開いて意思決定するための画面ではない。

**提案**: 復習タブの最上部に1行のサマリだけを出す
（例: `今日の残り 約12分 · 想定得点 47点 · 合格まであと13点`）。分析タブは週末のレビュー用として現状維持。

### 課題10 難易度3の母数不足（2026-09-01 実測により内容を訂正）

**当初の記述（誤り）**: 「difficulty は実質2段階なので、時間の基準は `studyMode × 章` に変えるべき」

**訂正**: §3.0 の実測では **難易度1が約1.9分、難易度2が約5.3分と2.8倍の差**があり、
difficulty は所要時間の予測子として十分に機能していた。基準から外すべきではない。
時間の基準は **`難易度 × studyMode` の両方**を使う（課題1の提案Aに反映済み）。

**残る問題**: 440問の difficulty 分布は **1:211 / 2:217 / 3:12**。難易度3は12問しかないため、
`quadrantMatrix` の帯3の中央値は母数不足で不安定、あるいは `null` になる。
帯3は独立した基準を持たず、**帯2の値を係数倍して代用する**（既定値表では 5.5分 → 9分）。

### 課題12【重要】「遅い」の判定が中央値超のため、構造的に約半数が「遅い」になる

**証拠**: `analytics.ts` `quadrantMatrix` —

```ts
const slow = ratio > 1 // 中央値超で「遅い」
```

**帰結**
中央値で切っているので、**定義上つねに約半数が「遅い」側に落ちる**。§3.0 の実測が
A・速い100 / A・遅い71 とほぼ50/50に割れているのは、この構造そのものであり、
「71問に速度の問題がある」という意味ではない。

さらに深刻なのは**表示と実装の意味がずれている**こと。カード下部の文言は
「『A・遅い』はCBT本番（1問約5分）で失点しやすい隠れ弱点です」だが、実装は本番の5分ではなく
**その難易度帯の中央値**で判定している。難易度2は中央値5.3分でたまたま5分に近いが、
**難易度1は中央値1.9分なので、4分で解けていても「本番で失点しやすい」と警告される**。
難易度1（211問・全体の48%）の「A・遅い」判定は大半が誤検出である。

**提案**: `slow` の基準を中央値から**本番の持ち時間**に変える（A問題5分・B問題10分）。
カードの文言が元々意図していた意味に実装を合わせるだけで、追加のデータは要らない。
中央値比の表示自体は「同程度の問題と比べてどうか」の情報として有用なので残す。

### 課題13【重要】解答時間の計測上限30分が緩すぎ、中断が実データに混入している

**証拠**
- `timer.ts` — `export const MAX_DURATION_SECONDS = 30 * 60`
- §3.0 の「時間超過の訓練対象」上位3件が **29分51秒 / 28分13秒 / 27分38秒** と、
  いずれも30分の上限直前に貼り付いている。3件とも難易度2（中央値5.3分）の問題。

**帰結**
電験3種の問題を28〜30分連続で解いたとは考えにくく、**開いたまま中断された記録**とみるのが自然。
`visibilitychange` による一時停止は、画面を消さずに端末を置いた場合には発火しない。
育児中は中断が常態であり、この上限では中断時間が解答時間として記録され続ける。

上限を超えた記録は `elapsedSeconds` が `undefined` を返して破棄されるため、
**同種の記録がさらに何件か失われている**（着手232問に対し計測207問。差25問の一部がこれに当たる）。

この汚染は2箇所に効く: (a) 「A・遅い」ランキングの上位が中断の痕跡で埋まり、
「直前期の訓練対象」としての用をなさない。(b) **課題1の時間予算モードが同じデータを使う**ため、
見積もり精度に直結する。

**提案**
- 記録時の上限を「**その難易度帯の中央値の3倍**、または**15分**の小さいほう」に下げる
  （難易度2なら15分、難易度1なら約5.7分）
- 既存履歴に残っている外れ値は削除せず、**見積もり計算時にクリップして**扱う
- `ProblemViewer` に明示的な「中断」ボタンを置く（課題8の記録ボタン追加と同じ改修に含められる）

### 課題11 重要度が実質的な定数になっている（参考）

**証拠**: importance の分布は **1:4 / 2:70 / 3:366**。83%が3。
`reviewValue` の `importanceWeight`（0.6 / 1.0 / 1.4）はほぼ全問1.4となり、並び順への寄与がほぼない。

  → **最も筋が良い**（実測ベース・既存データだけで可能）。ただし解像度は章単位まで

## 6. 決定事項（2026-09-01 ユーザー回答）

1. **目標モードの既定**（課題2）: **合格ライン到達（`passingScore` + 10点マージン）を既定にする。**
   達成後に「全問A以上」へ自動昇格する。
2. **`request_retention` の引き下げ**（課題5）: **0.85 を採用する**（「合格に届くなら」という条件付き）。
   条件を満たすための実装上の前提を3つ置く:
   - **試験60日前から 0.9 へ戻す。** retention は「その実施日から試験日までの残日数」で決める。
     こうすれば `deriveFromHistory` が履歴を再生するたびに同じ結果になり、決定的性が保たれる。
   - **`reviewPlan.ts` の `R_MID` を `request_retention` と連動させる。**
     現在 `R_MID = 0.9` がハードコードされており（コメントも「FSRSの目標保持率90%を基準にする」）、
     retention だけ 0.85 にすると**FSRSが「予定どおり」と判断した問題が期限当日に全部
     🟡そろそろ と表示され、リスク帯が機能しなくなる**。
   - **監視指標**: 分析タブの学習曲線の「復習の正答率」（`weeklyLearningCurve` の `reviewRate`）。
     0.85 なら理論上85%付近に収束する。大きく割れたら 0.9 へ戻す。
     `deriveFromHistory` により**いつでも巻き戻せる＝不可逆な変更ではない**。

   なお §3 課題5 に書いた「復習発生が約39%減」はスケジュール上の計算であり、額面どおりには効かない。
   忘却が進んだ状態で復習するぶんC評価と lapse が増え、stability が下がって復習が戻ってくる。
   **実効の節約は 20〜30% 程度**とみておく。それでも、浮いた時間を未着手へ回す価値のほうが
   大きい段階である（着手52.7%・§3.0）。
3. **時間予算チップの刻み**（課題1）: `5分 / 15分 / 30分 / 指定なし` で開始し、運用して問題が出たら修正する。
4. **S の試験前最終確認**（課題4）: **試験日の21日前**に1回だけ復習キューへ戻す。
5. **出典タイトルの補記**（課題6）: **実施する。ただし最終フェーズ（Phase E）で行う。**
   当初は「効果が出るのは年度別演習を開始する2026年11月以降だから、それまで見送る」と整理したが、
   **11月という日付では待たない**。Phase A〜D を終えた時点で、時期に関わらず着手する。
   順序は **静電気(72問) → 電気計測(42問) → 三相交流(22問)** と、出題比率の大きい章から埋める。
   （※着手前にオーム社の原本に出典表記があるか1ページ確認すること。表記があれば転記のみで
   約25分、無ければ1問ずつ調べることになり工数の桁が変わる）
6. **既定の所要時間**（課題1・提案A）: §3.0 の実測に基づき **難易度1: calc 2分 / memory 1.5分、
   難易度2: calc 5.5分 / memory 2.5分、難易度3: calc 9分 / memory 3分** とする。

## 8. Phase D の実測（2026-09-01・ts-fsrs@5.4.1）

§3 課題5 の「採用前にインストール済み ts-fsrs@5 の実装で数問ぶん実測して確認すること」
に対する結果。**§3 の試算表（間隔1.64倍・復習39%減）は、実際の ts-fsrs の挙動とは合わない。**
以下を実装の根拠とする。

### 8.1 request_retention を 0.85 にしたときの間隔

起点 2026-09-01・空カードから同じ評価を繰り返したときの次回間隔（日）。

| 回 | 全部B(Good) 0.90 → 0.85 | 全部A(Easy) 0.90 → 0.85 |
|---|---|---|
| 1 | 3 → 4（1.33倍） | 8 → 16（2.00倍） |
| 2 | 14 → 31（2.21倍） | 66 → 189（2.86倍） |
| 3 | 57 → 173（3.04倍） | 397 → 1546（3.89倍） |
| 4 | 196 → 773（3.94倍） | 1875 → 9368（5.00倍） |

§3 の表は「同じ安定度 S に対する1回ぶんの間隔比」を出したもので 1.64倍だったが、
実際は **初回で1.33倍にとどまり、回を重ねるほど比が開く**（間隔が延びると次回の
stability の伸び方も変わるため、単発の式では効果を過小にも過大にも見積もる）。
単発の比から復習回数を出す計算は使えない。

### 8.2 試験日までに実際に発生する復習回数（clipDueToExam 込み）

意味のある指標はこちら。起点 2026-09-01 → 試験 2027-02-15（167日）で、期限が来たら
必ずその日に復習する前提で1問あたりの発生回数を数えた（`clipDueToExam` 適用後）。

| 評価の並び | 0.90固定 | Phase D（0.85／60日前から0.9） | 削減 |
|---|---|---|---|
| 全部B | 4回 | 3回 | −25% |
| 全部A | 3回 | 2回 | −33% |
| C→以降B | 6回 | 5回 | −17% |

**試験日クリップが上限になるため、8.1 の間隔比は額面どおりには効かない。**
実効の削減は **17〜33%** で、§6-2 で見込んだ「20〜30%程度」とほぼ一致する。採用の判断は
そのままでよい。なお B と C を交互に繰り返す（lapse を出し続ける）問題は 0.90固定でも
Phase D でも毎日 due になり、削減はほぼ0%。**節約が効くのは定着している問題だけで、
落とし続けている問題の負荷は下がらない**（下がってはいけない）。

### 8.3 R_MID を連動させないと何が起きるか

retention 0.85 で組んだスケジュールの期限当日の R と、そのときのリスク帯。

| 回 | 期限当日の R | R_MID=0.90 固定 | R_MID=retention 連動 |
|---|---|---|---|
| 1 | 0.858 | 🟡 そろそろ | 🟢 余裕 |
| 2 | 0.850 | 🟡 そろそろ | 🟡 そろそろ（境界） |
| 3 | 0.850 | 🟡 そろそろ | 🟡 そろそろ（境界） |

**0.90 固定のままだと「予定どおりの問題」が期限当日に軒並み🟡になり、帯が優先度として
機能しなくなる**（§6-2 の懸念どおり）。連動させると、0.90 のときと同じ「予定どおり＝境界付近／
遅れるほど🟡→🔴」の分布に戻る。期限当日の R は目標値ちょうど付近に着地するので🟢と🟡の
境界を跨ぐが、これは 0.90固定・retention 0.90 の現行でも同じ挙動（0.881 / 0.899 / 0.900）で、
新しく生じた揺れではない。

### 8.4 決定的性の確認

`retentionFor` は「その実施日から試験日までの残日数」だけで決まるため、`deriveFromHistory`
が `review_history` を再生しても結果は同じになる（履歴の並びを逆にしても出力一致を確認）。
切り替え点は残60日ちょうど（試験 2027-02-15 なら 2026-12-17 以降が 0.9）。
すでに発行済みの `due_date` は次にその問題を記録するまで再計算されないので、
60日前を跨いだ瞬間に予定が一斉に前倒しされることはない。

### 8.5 S の試験前最終確認の境界

試験 2027-02-15・21日前＝2027-01-25。

| S を記録した日 | due_date |
|---|---|
| 2026-09-01 | 2027-01-25 |
| 2027-01-24 | 2027-01-25 |
| 2027-01-25 以降 | null |
| 試験日未設定 | null |

最終確認日を過ぎてから S を付け直した場合に null にするのは、過去日を due にすると
**翌日以降も毎日 due に居座り、S が「復習不要」の意味を失う**ため。
また、最終確認で復習キューに載った S は `reviewValue` の重み（S=0.25）で忘却リスク順に
並ぶ。重み未設定（価値0）のままだとキュー最下段に沈み、Phase B の時間予算線から
外れて結局やらないことになる。

## 9. Phase F 実施記録（2026-09-02）

### 9.1 スコープ ―― b・d を先に出し、c は別PRにする

§3 課題7 は a〜d の4段で、a（`display: standalone`）は Phase A で実施済み。
残る b〜d について、**設計書は「b)〜d) は独立したPRにする」としている**ので、
本PRは **b（アプリシェルのオフライン化）と d（記録のオフラインキュー）** に絞り、
**c（問題画像の先読み）は別PR**とした。

この切り方にした理由は、bとdが単独では成立しないためである。

- **b だけでは意味がない。** service worker がシェルを返せても、学習データ（`denken_reviews`）は
  Supabase から毎回取得している。オフラインで起動しても**画面は空になる**。
  設計書の課題7 は a〜d のいずれもこの点に触れておらず、**設計の穴**だった。
  そこで b と対にして、**学習データのローカルキャッシュ**（IndexedDB のスナップショット）を入れた。
- **b だけ入れて d を入れないのは危険。** シェルとデータが返るとオフラインでも操作できてしまい、
  そこで付けた A/B/C の記録は `console.error` を吐いて消える。**「使えるように見えて記録が消える」**
  という、今より悪い状態を作ってしまう。b を入れるなら d は同時に要る。
- **c は独立している。** 画像は `ProblemViewer` の中で完結し、b・d と依存しない。
  一方で署名URL（TTL 3600秒）を跨いだキャッシュ設計が要り（§9.4）、規模も別なので分けた。

### 9.2 アプリシェル（課題7b）: ビルドツールを足さない手書きSW

`vite-plugin-pwa` / workbox は**入れなかった**。理由は、Vite の成果物が
`/assets/index-<hash>.js` とハッシュ付き＝**URLが不変**なので、
「precache リストをビルド時に生成する」動機がそもそも無いこと。初回アクセス時の
runtime caching で同じ結果になり、依存も build 設定も増えない。

`public/sw.js`（96行）の方針:

| 対象 | 戦略 | 理由 |
|---|---|---|
| ナビゲーション（HTML） | network-first → キャッシュ済み `index.html` | `index.html` はハッシュが付かない。オンラインなら必ず最新を見る |
| 同一オリジンの静的ファイル | cache-first | URLが不変なので古い内容を掴む事故が起きない |
| 別オリジン（Supabase の API・認証・Storage） | **介入しない** | 認証トークン付きのレスポンスと TTL 付き署名URLをキャッシュに残さないため |

更新は `VERSION` を上げると旧キャッシュを捨てる。`skipWaiting` + `clients.claim` で即座に
置き換え、`lib/swRegister.ts` が `controllerchange` を受けて**1度だけ**リロードする。
初回インストール時は「まだ誰も制御していない」ため、この リロードは走らない。
開発（`vite dev`）では登録しないだけでなく、**残っているSWを解除する**
（本番→dev の行き来でキャッシュに掴まれ「直したのに変わらない」を防ぐ）。

実測（`vite preview` + Chromium・ネットワーク遮断してリロード）:

```
SW registered: { scope: 'http://127.0.0.1:4173/', active: true }
caches: [ 'electricpro-shell-v1' ]
cached: [ '/', '/index.html', '/assets/index-*.css', '/assets/index-*.js', '/favicon.svg' ]
offline reload → #root に 866 文字を描画（オフラインでもアプリが起動する）
```

### 9.3 学習データと記録（課題7d）: IndexedDB に「スナップショット」と「送信待ち」

`src/lib/offlineStore.ts`（純粋な入れ物・Supabase と React に依存しない）に2つだけ持つ。

| ストア | 内容 | 使いどころ |
|---|---|---|
| `snapshot` | `${userId}:${examId}` ごとの `reviews` / `plans` 一式 | 起動時にサーバ取得を待たず即描画する |
| `outbox` | `denken_reviews` の upsert 待ち行列 | オフライン・送信失敗時に積み、復帰時に古い順で送る |

設計上の要点:

- **`outbox` のキーは `${userId}:${examId}:${questionId}`。** 同じ問題への連続記録は
  `put` で後勝ちに畳まれる。これは現行の「最後の書き込みが勝つ」方針そのままで、
  §3 課題7d が「相性が良い」と書いていた通りに素直に実装できる。
- **送信は1件でも失敗したらそこで止める。** 順序を保ったまま次の機会へ持ち越す。
- **スナップショットはローカルの記録でも書き戻す。** サーバ取得の直後だけに限らないので、
  オフラインで付けた記録も次回起動時にそのまま見える。
- **「どの対象のデータか」を ref で持つ**（`reviewsLoadedKeyRef` / `plansLoadedKeyRef`）。
  ①届いた新しいデータを古いスナップショットで上書きしない、②資格を切り替えた直後に
  別の資格のデータをその資格のスナップショットとして保存しない、の2つに使う。
  資格の切替時は `reviews` / `plans` を空に戻し、取得に失敗しても前の資格の記録が残らないようにした。
- **IndexedDB が使えない環境**（プライベートモード等）では全関数が「何もしない」に縮退する。
  オフラインの補助機能のために、本体の記録操作を失敗させない。

保存経路は `saveReview` に一本化した（`saveDetails` が同じ upsert を重複して持っていたため）。
これで**メモの保存もオフラインキューに乗る**。

UI はヘッダに1つだけ。オフライン中は「オフライン・未送信N件」、
オンラインで積み残しがあれば「未送信N件」。**「使えない」ではなく「あとで送る」**と読める文言にした。

### 9.4 残り（別PR）: 課題7c 問題画像の先読み

`ProblemViewer` は表示のたびに `signedUrl()`（TTL 3600秒）を発行して画像を取りに行くため、

## 10. 課題7c 実施記録（2026-09-02・Phase F-2）

### 10.1 鍵の問題 ―― 署名URLはキャッシュの鍵にならない

問題画像は非公開バケットにあり、表示のたびに TTL 3600秒の署名URLを発行して取りに行く。
署名URLは**発行のたびに別の文字列**なので、それをキャッシュの鍵にすると次のセッションでは
必ずミスする。§9.4 の見立てどおり、鍵と実体を分ける必要がある。

採った形は次の1本である。

```
鍵   : /__problem-image/{encodeURIComponent(storage_path)}   ← 同一オリジン・TTL に依らず不変
実体 : Supabase から落とした Blob を Cache Storage に置く
表示 : <img src="/__problem-image/..."> を service worker が cache-only で返す
```

`storage_path` は `{user_id}/theory/{chapter}/{filename}` で、その画像を一意に決める。
署名URLが1時間で無効になっても鍵は変わらないので、**翌日でも・オフラインでもヒットする**。

### 10.2 SW側（`public/sw.js` +16行）

- `/__problem-image/` を **cache-only** で返す分岐を、静的ファイルの分岐より前に置いた。
  storage_path は `.png` で終わるため、順序を誤ると既存の cache-first 分岐（`isImmutableAsset`）に
  食われ、実在しないパスをネットワークへ取りに行ってしまう。
- ミス時はネットワークへ回さず 504 を返す。このパスはサーバ上に実在せず、SW以外に
  応答できる者がいない（ページ側は未キャッシュなら合成URLを使わないので通常ここには来ない）。
- `activate` の掃除を「`SHELL_CACHE` 以外を消す」から **`KEEP_CACHES` に無いものを消す**へ変えた。
  これが無いと、アプリシェルの `VERSION` を上げた瞬間に**先読み済みの画像が全部消える**。
  画像キャッシュはシェルとは別の版（`electricpro-problem-images-v1`）で持つ。

### 10.3 ページ側（`src/lib/problemImageCache.ts` 新規）

| 関数 | 役割 |
|---|---|
| `prefetchProblemImages(ids)` | 「今日の分」の先読み。返り値は中断関数 |
| `resolveImageSrc(path)` | 表示に使うURLを決める（キャッシュ済み→合成URL／未→署名URL） |
| `loadProblemAssets(qid)` | 座標（`denken_question_assets`）を network-first で読む |
| `clearProblemImageCache()` | ログアウト時に丸ごと捨てる |

設計上の要点:

- **座標も一緒にキャッシュする。** 画像だけあってもマスク位置（`answer_x_pct` 等）が決まらず
  オフラインでは描画できない。同じ Cache Storage に JSON として置く（`/__problem-assets/{qid}`）。
  DBが唯一の正なので **network-first**（オンラインなら必ず最新を見る・データ修正はSQLで入る）、
  取得に失敗したときだけ前回の内容に落ちる。
- **索引を別に持たない。** 上限管理（40MB）に要る「大きさ」と「いつ入れたか」は、
  キャッシュに入れる `Response` 自身の `content-length` / `x-cached-at` ヘッダに持たせた。
  IndexedDB に索引を作ると、索引と実体がずれる状態を新たに作ることになる。
  超過時は古い順に消し、**今回の先読み対象は保護する**（直後に使う画像を捨てない）。
- **「試した」印は着手の直前に付ける。** 今日のキューは記録のたびに作り直されるため、
  先読みは走る前に何度も捨てられる。上限に達した回・中断された回が印だけ残すと、
  その問題は以後どの回でも拾われない。着手時に印を付ければ、走った分だけが印になる。
- **未キャッシュの画像をその場で開いたときは、表示用の署名URLをそのまま写す。**
  表示は署名URLで先に始める（大きな見開きを落とし切るまで待たせない）。同じURLを使うので
  ブラウザのHTTPキャッシュが効き、二重ダウンロードになりにくい。
- **1枚ごとに失敗を許す**（`ProblemViewer`）。オフラインでは「先読み済みの枚だけでも開く」方が
  役に立つ。1枚も出せないときだけ、次に何をすればよいかを書いたメッセージを出す。
- **縮退する条件**: Cache Storage が使えない／SW が制御していない（開発・未対応環境）／
  データセーバー指定／オフライン。いずれも**従来どおり署名URLで表示するだけ**に戻る。

### 10.4 先読みの対象と上限

対象は「今日のキュー」＝復習due＋新規着手枠（課題3で1つにまとめたもの）で、
画像が登録され得る問題（`hasKnownAsset`）だけ。上限は 1回40問・合計40MB・同時2本、
実行は `requestIdleCallback`。**隙間時間の操作と帯域を奪い合わせない**ための値である。

## 14. Phase J 実施記録（2026-09-03）— 問題表示の端末フィットと解答選択

### 14.1 課題16 「拡大」が端末ごとの当たり外れになっている

分野別の問題ビューアは、見開き画像（2360×1640）を **画面幅に対して 100% か 190% か**の
2択で描いていた。190% は「10インチのタブレットで左ページが画面幅ちょうどになる」ことを
基準に決めた固定値で、次の2つを取り違えている。

1. **必要なのは倍率ではなく「読む範囲を画面幅に合わせること」**。実際に読むのは見開きの
   左ページ（`answer_x_pct`%）だけで、右は解答マスクに覆われた余白である。画面幅の半分を
   マスクに使ったまま倍率だけを上下させても、端末が変われば当たり外れが出る。
2. **倍率が毎回リセットされる**。開くたびに＋を押す操作が、1問あたり数十秒の隙間時間
   （§2 の前提）に毎回乗っていた。

同じ構造が年度別（CBT）の 180% 固定にもあった。

### 14.2 直した内容

**① 読む範囲を画面幅に合わせる（自動フィット）**

`ProblemViewer` は画像を `100 / answer_x_pct` 倍に引き伸ばし、外側を `overflow-x: hidden` で
切る。標準の見開き（50）なら2倍＝**左ページが画面幅ちょうど**、全面問題（100）は等倍。
倍率が端末幅から決まるので、スマホ・タブレット・PCのいずれでも初期表示のまま読める。
広い画面では 1ページ 820px で頭打ちにし、中央寄せにする（引き伸ばしてもぼやけるだけ）。

短い問題（`answer_y_pct` < 100）は、左ページ下部の白いマスクを描く代わりに**高さごと
切り落とす**。2倍表示では空白のスクロールがそのぶん長くなるため。

解答表示中は倍率を変えず、右ページへ横スクロールして読む（見開き全体を出すために
縮小すると、拡大した意味が消えるため）。横に続くことは画面から読めないので一言添える。

**② 倍率は端末ごとに記憶する**（新規 `src/lib/viewerZoom.ts`）

自動フィットを 100% とし、そこからの微調整（75%〜300%）を `localStorage` に持つ。
スコープは分野別（`bunya`）と年度別（`cbt`）で分ける。見開きと縦長ページでは
好みの倍率が別だから。年度別（`PaperImage`）も boolean の 180% 固定からこの倍率へ移した。

**③ 問題画面で解答を選べるようにする**

`ProblemViewer` の下部に (1)〜(5) を追加した。**解答を見る前に自分の答えを1つ確定させる**
ための操作で、本番CBT（`CBTRunner`）と同じ手順を分野別にも持ち込む。

自動採点はしない。分野別は正答データを持たず（`MasterQuestion` に正答は無い）、
正答表を新設すれば画像とデータの二重管理になる。選んだ番号は `ReviewHistoryEntry.choice`
に残すだけで、正誤の判断は従来どおり解答画像を見た上での理解度（A/B/C/S）が担う。

### 14.3 やらなかったこと

- **ピンチズーム**。倍率を記憶する以上、ピンチの一時的な拡大とどちらが正かが曖昧になる。
  まず自動フィットで「そのまま読める」状態を作り、運用して足りなければ足す。
- **正答の自動採点**。年度別（`PaperDefinition`）が持つ正答を出典リンク経由で分野別へ
  引き当てる案はあるが、対応が付くのは収録済みの年度に出た問題だけで、
  「採点される問題とされない問題」が混ざる。二重管理を避ける方針（§5.2）も崩れる。

### 14.4 追補 — 解答は「切り替え」、選択肢は撤去

運用してすぐ2点の指摘。

**(a) 解答を見るのにスクロールの手間が多い。ボタン1つで切り替えたい。**

Phase J では「倍率を保ったまま右ページへ横スクロール」としたが、解答を見るたびに
横へ送り、戻すときにまた送り返す操作が要る。隙間時間に1問ずつ触る使い方では、
この往復が実際の負担になる。

倍率ではなく**切り出す範囲そのものを切り替える**形に変えた。画像は同じまま、
「どの矩形を画面幅いっぱいに描くか」を差し替える:

| | 問題表示 | 解答表示 |
|---|---|---|
| 標準の見開き | 左ページ（上部） | 右ページ |
| 短い問題（`answer_y_pct`<100） | 左ページ上部 | 左ページ下部 ＋ 右ページ |
| 全面問題（`answer_x_pct`=100） | 見開き全体 | 続きの「丸ごと解答ページ」 |

表示は `Rect{x0,x1,y0,y1}`（画像全体に対する%）1つを外枠の幅いっぱいに描く
`CropImage` に一本化した。マスクの白い矩形を重ねる実装は不要になり消えている
（範囲外は枠で隠れるため）。切り替え時はスクロール位置を先頭へ戻す。

**(b) 解答の選択肢 (1)〜(5) は不要。**

正答を記録して採点するなら要るが、画面で解答画像を見て確認する現在の使い方では
押す意味がない。UI・`ReviewHistoryEntry.choice`・`updateStatus` の引数ごと撤去した。
正誤は従来どおり理解度（A/S を正解として正答率を集計・§7.7）が担う。

自動採点を入れるなら、分野別に正答データを持たせるところからの別作業になる
（§14.3「やらなかったこと」の判断は据え置き）。
