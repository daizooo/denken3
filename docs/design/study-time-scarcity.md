# 学習時間が逼迫した状況で合格効率を最大化するための改善設計

作成: 2026-09-01 / 対象: 電験3種・理論（2027年2月受験）

本書は「アプリ全体を調査し、**学習時間が極端に減った前提**で、合格までの効率をさらに
上げられる箇所はどこか」を洗い出した調査記録と改善設計である。実装は本PRのスコープ外
（§6 の未決事項に回答が出てから、Phase ごとに別PRで行う）。

---

## 1. 背景 — 何が変わったか

`docs/design/expansion-design.md` §7.2 は、既に「産後1年程度は学習キャパシティが不確定」
という前提を織り込んで設計されている（事前宣言型の休止期間を廃止し、EWMA による適応推定へ）。
その判断は正しく、**時間が減ること自体には既に強い設計**になっている。

しかし実際に子どもが生まれ、学習時間が「減った」だけでなく「**細切れ・不規則・予測不能**」に
なったことで、別の種類のズレが表面化する。

| 変化 | 既存設計が想定していたこと | 実際に起きること |
|---|---|---|
| 総量が減る | EWMA が自動追従する ✅ | 対応できている |
| **1回の長さが読めない**（5分／30分／ゼロ） | 未対応 | 「今日の推奨7問」が実時間で何分か分からない |
| **開いてから決める時間がない** | 未対応 | タブ移動・絞り込みの操作自体が隙間時間を食う |
| **中断が常態**（片手・抱っこ・寝かしつけ） | 一部対応（タイマーの pause） | 記録までのタップ数・オフラインが効く |
| 目標水準 | 「全問A以上」＝ 440問 | 合格（60点）に必要な水準と乖離し、常時「遅延」判定 |

**本書の中心的な主張は1つ**: 現行アプリの計画単位はすべて「**問題数**」であり、
逼迫しているのは「**分**」である。この単位のズレが、以降に挙げるほとんどの課題の根にある。

## 2. 現状の到達点 — 改善不要と確認した点

調査の結果、以下は既に十分よくできており、**触らない**ほうがよいと判断した。

1. **ペースの適応推定（EWMA・半減期14日）** — `src/lib/pace.ts`。
   事前にキャパシティを宣言させない設計は、育児下の前提として明確に正しい。休んだ日も0問として
   算入されるため、休止が自動的に織り込まれる。
2. **「上限で切らず、線を引く」復習UI** — `planDailyReviews` の推奨ラインと
   「以降は順番待ち（遅れではありません）」の文言。罪悪感を出さない設計として妥当。
3. **遅延を赤字で出さない** — `QuestionCard` は「N日遅延」ではなく忘却リスク帯
   （優先／そろそろ／余裕あり）で表示する。FSRS が経過を織り込む以上これが正しい。
4. **FSRS の試験日クリップ＋直前期テーパー** — `clipDueToExam`。試験後に復習が漏れる問題と、
   直前期に間隔が開きすぎる問題の両方を潰しており、追加不要。
5. **履歴からの再導出（`deriveFromHistory`）** — アルゴリズムやパラメータを後から変えても
   `review_history` から全状態を再計算できる。**§3 の課題5（保持率の変更）を安全に試せるのは
   この設計のおかげ**であり、既存設計の最大の美点。
6. **想定得点の出題比率の代理** — `estimateScore` は「オーム社問題集の収録数比」を出題比率の
   代理としているが（設計書 §7.7(4) が「年度別の topic 集計で置き換える」としていた箇所）、
   収録済みの年度別6回分（R5上〜R7下・108問）の `topic` と突き合わせたところ、**実測と
   ほぼ一致していた**。ここは置き換え不要と判断する。

   | 分野 | 収録数比（現行の代理） | 年度別6回の実測（問数ベース） |
   |---|---|---|
   | 電気回路（dc/trans/ac1/ac3） | 174/440 = 39.5% | 45/108 = 41.7% |
   | 電磁気（elec/mag） | 127/440 = 28.9% | 32/108 = 29.6% |
   | 電子理論（etheory/ecircuit） | 94/440 = 21.4% | 21/108 = 19.4% |
   | 電気及び電子計測（meas） | 45/440 = 10.2% | 10/108 = 9.3% |

   （実測はB問題の配点2倍・選択問題の非選択分を補正していない問数ベースの近似。傾向の確認には十分）

## 3. 発見した課題

優先度順。各項に「証拠（コード上の該当箇所）」「帰結」「提案」を書く。

### 課題1【最重要】計画の単位が「問題数」で、「分」ではない

**証拠**
- `planDailyReviews()` の戻り値は `recommendedCount`（問数）。
- `analyzePace()` の `currentPace` / `requiredPace` / `recommendedNorm` はすべて「問／日」。
- 時間（`duration_seconds`）を扱っているのは `analytics.ts` の `quadrantMatrix`（事後分析）だけで、
  **計画側は時間を1秒も見ていない**。
- `reviewValue()` のスコアは `理解度 × 重要度 × (0.15 + 忘却リスク)`。**コスト（所要時間）の項がない**。

**帰結**
- ヘッダの「今日の推奨 7問」が、実時間で10分なのか70分なのか分からない。15分しか取れない日に
  7問は達成不能で、未達が続くと `verdict='behind'` → `needsReplan` → 「遅延が続いています」バナー。
  **時間軸のズレのせいで、適応設計であるはずのペース分析が慢性的な遅延判定を出す。**
- 価値順に並べているため、キューの先頭に「10分かかる計算問題」が来ることがある。5分しかない日に
  開くと、**着手できずに終わる**。時間が希少なときに最適な貪欲順は価値そのものではなく
  「**価値 ÷ 所要時間**」である（1分の暗記問題2問のほうが、10分の計算問題1問より期待得点が高い場面がある）。

**提案A: 所要時間の推定（新規 `src/lib/estimateMinutes.ts`）**

推定の優先順:
1. その問題自身の実測（`review_history` の `duration_seconds` の中央値）
2. 同じ `studyMode × 章` の実測中央値
3. 既定値（calc 8分 / memory 2分・実測が溜まるまでの初期値）

データ源は既に完成している（`§7.6` の計測が `duration_seconds` として蓄積中）。新規の計測UIは不要。

**提案B: 時間予算モード（新規 `src/features/questions/TimeBudgetBar.tsx`）**

復習タブ上部に `[5分] [15分] [30分] [指定なし]` のチップを置く。選ぶと、
- キューを「価値 ÷ 推定所要分」の降順に並べ替え、
- 累積推定時間が予算に達したところに線を引く（**現行の推奨ラインの一般化**であり、UIの新概念を増やさない）。

「いま何分ある？」に答えるだけで、その予算で期待得点の伸びが最大になるセットが出る。これが
本書で提案する改善のなかで**最も効果が大きい**。

**提案C: 既存の表示を「分」でも出す**

「今日の推奨 7問（およそ42分）」のように併記する。ペース分析の主要指標にも「現在ペース 12分/日」を追加。

**実装規模とコンフリクト影響**（CLAUDE.md のコンフリクト最小化方針に沿って評価）
- 新規ファイル2つ＋ `reviewPlan.ts` への**関数追加**（既存関数は変更しない）
- `App.tsx` の変更は 20行程度（チップの state と `filteredQuestions` の並び替え差し替え）

### 課題2【重要】目標が「全問A以上（440問）」で、合格に必要な水準と乖離している

**証拠**
- `pace.ts` 冒頭: 「ゴールの定義: 『全問に着手した』ではなく『全問が A 以上』」。
- `remainingQ = 440 - masteredQ`。分母が440問で固定。

**帰結**
理論の合格は60点（18問中おおむね11問正解）。440問すべてA以上は「合格」ではなく「満点狙い」の目標。
時間が潤沢なら健全な目標だが、育児下では**到達不能な目標に対して毎日 behind と判定される**。
`estimateScore()`（想定得点）は既に実装済みなのに、**ペースの目標には接続されていない**のがもったいない。

**提案: 目標モードを2つ持つ**
- `pass`（合格ライン到達・**新設**）: `estimateScore` が `passingScore + マージン`（既定 +10点）に
  届くために必要な最小の問題集合を求め、それを `remainingQ` の分母にする。
  `ChapterImpact.impact`（章を全問A相当にしたときの総得点への寄与）が既にあるので、
  **インパクト降順に積み上げるだけで実装できる**。
- `mastery`（全問A以上・現行）: `pass` を達成したら自動でこちらへ昇格。

**効果**: 「合格まであと◯点／あと◯問」が出る。育児下で最も効く動機づけであり、同時に
`replanOptions` の `narrow`（現状は文章だけで、押せるボタンではない）を実行可能な機能に変える。

### 課題3【重要】新規着手と復習が別画面で、「今日やること」が1画面にまとまっていない

**証拠**
- `App.tsx` の `baseQuestions`: 復習タブは `r.due_date` を持つ問題だけを通す。
  未着手（`due_date=null`）は**復習タブに絶対に出てこない**。
- 一方、新規着手のノルマ（`pace.recommendedNorm`）は**分析タブにしか表示されない**。

**帰結**
5分の隙間にアプリを開いて「今日の復習はありません」と出ても、実際には新規着手を進めるべき日がある。
ユーザーが自分でタブを移動し、絞り込みを開いて未着手を選ぶ必要がある。**隙間時間の相当部分が
「何をやるか決める操作」に消える。**

**提案**: 復習タブを「今日の学習」に一本化する。
1. 復習due（価値順）を先頭に置き、
2. その後ろに新規着手候補（推奨ノルマ数・章の学習順）を同じキューとして継ぎ、
3. 課題1の時間予算の線をキュー**全体**に引く。

新規と復習の区切りは小見出し1行で示すだけでよい（現行の推奨ラインと同じ見た目）。

**併せて修正したい軽微な不整合**
`reviewDueCount()` は今日タブで `r?.status === '未着手'` を件数に含めるが、`baseQuestions` は
未着手を除外する。つまり**章チップの件数と、実際に表示される問題数が食い違う**。
メモだけ保存した問題は `status='未着手'` の行が生成されるため、実際に起こり得る。

### 課題4 S（復習不要）にした問題が、試験まで一度も戻ってこない

**証拠**: `fsrs.ts` — `if (status === 'S') return { due_date: null, last_reviewed: eDate }`。

**帰結**: 時間がないとき「S」を多用するのは合理的な節約行動だが、S にした問題は `due_date=null` の
ため FSRS の忘却追跡から完全に外れ、**試験直前に一度も確認されない問題群**が積み上がる。
9月にSにした問題を2月の本番で落とす、という形で効いてくる。

**提案**: S にも「試験前の最終確認」を1回だけ入れる。`due_date = 試験日 - N日`（既定21日）。
`clipDueToExam` の直前期テーパーと同じ思想の自然な拡張。S の意味を「通常の復習キューから外す」に
留め、「試験前確認からも外す」は別操作（完全除外）として分ける。

### 課題5 FSRS の目標保持率が既定90%のまま — 時間予算に対して復習量が過大

**証拠**: `fsrs.ts` — `new FSRS({ enable_short_term: false })`。`request_retention` が未指定なので既定 0.9。

**分析**: FSRS-5 の想起確率式 `R(t) = (1 + FACTOR·t/S)^DECAY`（`DECAY=-0.5`, `FACTOR=19/81`）から、
同じ安定度 S に対する次回間隔は `t = S·(81/19)·(R⁻² − 1)`。

| request_retention | 間隔（Sを1としたとき） | 復習の発生頻度 |
|---|---|---|
| 0.90（現行の既定） | 1.00 | 基準 |
| 0.85 | 1.64 | −39% |
| 0.80 | 2.40 | −58% |

**1回勝負・試験日固定・学習時間が希少**という条件では、0.9 は保守的すぎる可能性が高い。
保持率を下げると1問あたりの想起確率は下がるが、**同じ時間で触れる問題数が増える**ため、
未着手を減らす効果のほうが大きい局面がある（特に現在のように未修得が多い段階）。

**提案**: `request_retention` を設定可能にし、既定 0.85、試験60日前から 0.9 へ戻す（直前期は精度優先）。

**注意**
- これは学習方針の根幹に触れるため **§6 の未決事項としてユーザー判断を仰ぐ**。
- 変更しても `deriveFromHistory` が `review_history` から全状態を再計算するため、過去データは壊れない。
- 上表は FSRS-5 標準の定数に基づく試算。採用前に、インストール済み `ts-fsrs@5` の実装で
  数問ぶん実測して確認すること。

### 課題6 年度別↔分野別のリンクが全件未設定で、誤答の前倒し復習が動いていない

**証拠**
- `boostReview()`（年度別で誤答した問題に対応する分野別問題の `due_date` を今日にする）は
  `App.tsx` に実装済みで、`MockExamView` に `onBoostReview` として渡されている。
- しかし `PaperQuestion.sourceQuestionId` は、収録済み6回分108問すべてで**未設定**
  （`_skeleton.ts` のコメント1件を除き0件）。つまり**この機能は一度も発火しない**。

**提案**: 手入力せず、ビルド時に自動リンクする。
分野別のタイトルには出典が入っている（例: `抵抗直並列回路（H16-A4/R6下-A7）`）。
`R6下-A7` → ペーパー問題 `r6-2_a07` へ機械的に解決できる。新規 `src/lib/sourceLink.ts`（純関数）を
追加し、`papers/index.ts` の既存ビルド時チェック（`validatePaper`）に相乗りさせる。

**実現可能性の実測**: 分野別タイトル中の `R5上`〜`R7下` の出典は **57件**。収録済み108問の
**約53%** を手入力ゼロで自動リンクできる。

**制約（先に埋めるべきデータの穴）**: 出典がタイトルに入っていない章がある。

| 章 | 収録数 | タイトル中の出典数 |
|---|---|---|
| 静電気（elec） | 72 | **0** |
| 三相交流（ac3） | 22 | **0** |
| 電気計測（meas） | 45 | **3** |
| （他6章） | 301 | 359 |

この3章（139問）はリンク不可。自動リンクの前に**タイトルへの出典補記**が要る（データ作業として別PR）。

### 課題7 オフラインで使えない／ホーム画面アプリとして起動しない

**証拠**
- service worker が存在しない（`src/`・`public/`・`index.html` に該当なし）。
- `public/manifest.webmanifest` の `"display": "browser"`。
- 問題画像は Supabase の非公開バケットの署名URL（TTL 3600秒）で毎回取得している。

**帰結**: 抱っこ中・寝かしつけ中・移動中など、**電波が弱く読み込み待ちが許されない場面こそが
隙間時間**である。今は起動のたびにネットワーク往復が要る。

**提案（段階的・後半ほど重い）**
- a) `"display": "standalone"` にする（**1行**。ホーム画面から即起動しブラウザUIが消える）
- b) アプリシェル（HTML/JS/CSS）を service worker でキャッシュ → 起動が即時になる
- c) 「今日の分」の問題画像を先読みして Cache Storage に置く（署名URLのTTLとの整合が要検討）
- d) 記録のオフラインキュー（IndexedDB）→ 復帰時に upsert。現行の「最後の書き込みが勝つ」方針と相性が良い

a) は単独で即実施可能。b)〜d) は独立したPRにする。

### 課題8 記録までの導線が1タップ多い

**証拠**: `ProblemViewer` に記録ボタンがない。「問題を解く」→ 解く → 閉じる → カードを探して A/B/C、
という往復になる。

**帰結**: 片手操作・いつ中断されるか分からない前提だと、この1タップと「カードを探し直す」視線移動が効く。
中断されて記録し損ねると、タイマーは日跨ぎで破棄され（`timer.ts`）、計測データも失われる。

**提案**: `ProblemViewer` の「解答を見る」の隣に A/B/C/S を置き、押したらそのまま閉じる
（解答時間の確定も同時）。既存の `updateStatus` をコールバックとして渡すだけで、ロジックの追加はない。

### 課題9 分析タブは「読む」設計で、隙間時間には重い

現在の分析タブは、ペース分析・弱点ランキング・学習曲線・4象限・想定得点・章別進捗と密度が高い。
情報としては良質だが、5分の隙間に開いて意思決定するための画面ではない。

**提案**: 復習タブの最上部に1行のサマリだけを出す
（例: `今日の残り 約12分 · 想定得点 47点 · 合格まであと13点`）。分析タブは週末のレビュー用として現状維持。

### 課題10 難易度の分解能が足りず、時間の基準として使えない（参考）

**証拠**: 440問の difficulty 分布は **1:211 / 2:217 / 3:12**。実質2段階で、難易度3は12問しかない。

**帰結**: `quadrantMatrix` は難易度帯ごとの中央値で「速い／遅い」を判定するため、帯3は母数が
最大12問（うち計測済みのみ）で中央値が不安定、あるいは `null` になる。

**提案**: 所要時間・速さの基準を `difficulty` ではなく **`studyMode × 章`** に変える。
実所要時間には難易度より calc/memory の差のほうが効く（暗記問題は1〜2分、計算問題は5〜10分）。
課題1の提案Aと同じ実装で解決する。

---

### 課題11 重要度が実質的な定数になっている（参考）

**証拠**: importance の分布は **1:4 / 2:70 / 3:366**。83%が3。
`reviewValue` の `importanceWeight`（0.6 / 1.0 / 1.4）はほぼ全問1.4となり、並び順への寄与がほぼない。

**帰結**: 実質、復習順は「理解度 × 忘却リスク」だけで決まっている。これ自体は妥当な順序だが、
「重要度で優先する」という設計意図は**機能していない**と認識しておく必要がある。

**対応の選択肢**
- (a) 現状を追認し、`importance` を並び順から外す（スコアを単純化する）
- (b) 出題頻度（タイトル中の出典件数）を重要度の代替として自動算出する
  → ただし課題6と同じデータの穴（3章で出典なし）に当たる
- (c) 年度別 `papers` の `topic` 集計から**章単位**の重みを与える
  → **最も筋が良い**（実測ベース・既存データだけで可能）。ただし解像度は章単位まで

## 5. Phase 分割

CLAUDE.md の「変更は狭く・小さく・単機能に閉じる」「大きな機能は新規ファイルで実現する」に従い、
各Phaseを独立してマージできる単位に切る。`App.tsx` の変更行数を各Phaseで明記する。

| Phase | 内容 | 新規ファイル | `App.tsx` の変更 |
|---|---|---|---|
| **A** | 即効の小改善: `display: standalone`（課題7a）／ProblemViewer から直接記録（課題8）／章チップ件数の不整合修正（課題3後半） | なし | 数行 |
| **B** | **本命**: 所要時間推定＋時間予算モード（課題1・10） | `lib/estimateMinutes.ts`, `features/questions/TimeBudgetBar.tsx` | 約20行 |
| **C** | 「今日の学習」の一本化（課題3）＋合格ライン目標モード（課題2） | `lib/passTarget.ts` | 約40行 |
| **D** | S の試験前最終確認（課題4）＋ `request_retention` の設定化と検証（課題5） | なし（`lib/fsrs.ts` に追記） | なし |
| **E** | 年度別↔分野別の自動リンク（課題6）。先行して出典タイトルの補記をデータPRで実施 | `lib/sourceLink.ts` | なし |
| **F** | PWA オフライン（課題7b-d） | `public/sw.js` 等 | 数行 |

Phase A は単独で先に出せる。Phase B → C は順序依存（Cの線引きがBの推定時間を使う）。
D・E・F は互いに独立で、いつでも差し込める。
