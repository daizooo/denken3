# 電子理論・電子回路の取り込みが完了していない原因（調査記録）

調査日: 2026-08-31 / 対象: `etheory`（電子理論）・`ecircuit`（電子回路）

## 1. 結論

**マッピング定義（`ASSET_MAP`）のキーが `newIMG_XXXX.png` のままなのに対し、
GoogleDrive 側のファイル名が `問N.png` 形式へ全面的に改名されたため、
分野別取り込みのファイル名完全一致が全滅し、1枚もアップロードされずに終わっていた。**

`ImportPanel` の分野別モードはドロップされたファイル名の**完全一致のみ**で紐付けるため、
一致0件のときは例外もエラーも出さず
「対象の画像が見つかりませんでした（N件は未登録/捨て問のためスキップ）」と表示して終了する。
このメッセージは「捨て問だから対象外」という正常系の文面に見えるため、
**失敗が失敗として見えない**（サイレント失敗）ことが、放置されていた理由でもある。

コード・マッピングデータ自体に誤りはない。取り込みが一度も成立していないだけである。

## 2. 事実確認

### 2.1 DB（`denken_question_assets`）

`split_part(question_id,'_',1)` で章別に集計した結果、`etheory` / `ecircuit` の行は **0 件**。
他の理論7章はすべて登録済み。

| chapter | rows | questions | files |
|---|---|---|---|
| dc | 71 | 69 | 70 |
| ac1 | 70 | 69 | 68 |
| trans | 16 | 14 | 15 |
| ac3 | 26 | 22 | 26 |
| elec | 78 | 72 | 74 |
| mag | 56 | 55 | 54 |
| meas | 51 | 45 | 50 |
| **etheory** | **0** | **0** | **0** |
| **ecircuit** | **0** | **0** | **0** |

### 2.2 Storage（`denken-problems`）

`{uid}/theory/` 配下の実ファイルは合計 **357枚**。
その内訳は dc 70 / ac1 68 / trans 15 / ac3 26 / elec 74 / mag 54 / meas 50 = 357 で過不足なく、
`etheory` / `ecircuit` のフォルダ自体が存在しない。
つまり **アップロード段階にすら到達していない**（DB登録だけ失敗したのではない）。

各章のアップロード日時:

- dc: 2026-07-21
- ac1 / trans / ac3 / elec / mag: 2026-07-22
- meas: 2026-07-24（08:00 に 0478〜0531、23:38 に 0534〜0537 を追加）
- etheory / ecircuit: **なし**

### 2.3 GoogleDrive 側のファイル名

親フォルダ `1MLAPR53Lwy16f1wDXEBqLRfN09I8XSRS` 配下の章フォルダ
（⓪電気の基本〜⑨電子回路）を確認したところ、**全章とも `問N.png` 形式**である。

- ⑧電子理論: `問1.png` 〜 `問46.png`、またがりは `問13-1.png` / `問13-2.png` 等（計50枚）
- ⑨電子回路: `問1.png` 〜 `問58.png`、またがりは `問9-1.png` / `問9-2.png` 等（計81枚）
- ⑦電気計測: `問1.png` 〜 `問51.png`（`問31,32.png` = 2問同居）
- ①直流回路: `問1.png` 〜 `問72.png`

さらに **Drive 全体を `newIMG` で検索してもヒット0件**。
旧命名のファイルはもう1つも残っていない。

Drive の章フォルダは 2026-08-03 07:52 に作成（＝再アップロード／整理）されており、
meas を取り込んだ 2026-07-24 より **後**である。
すなわち「①〜⑦は旧命名のうちに取り込み済み → その後 Drive を改名 → ⑧⑨は新命名しか手元に無い」
という時系列で、⑧⑨だけが取り残された。

### 2.4 コード側の該当箇所

`src/components/ImportPanel.tsx` の分野別ハンドラ:

```ts
const targets = all.filter(f => ASSET_MAP[f.name])   // 完全一致のみ
const skipped = all.length - targets.length
if (targets.length === 0) {
  setLog([`対象の画像が見つかりませんでした（${all.length}件は未登録/捨て問のためスキップ）。`])
  return
}
```

`ASSET_MAP`（`src/lib/assets.ts`）は9章分をマージした 472 キーで、
**そのすべてが `newIMG_XXXX.png`**（`src/data/*Assets.ts`）。
`問1.png` は1つもヒットしないため `targets.length === 0` となり、上記の分岐で即 return する。

対して**年度別（CBT模試）モードには逆引きのフォールバックがある**:

```ts
const m = filename.match(/問\s*(\d+)/) ?? filename.match(/(\d+)(?=\.[^.]+$)/)
return m ? paperByNumber.get(Number(m[1])) : undefined
```

年度別だけが `問N` 表記に対応していて、分野別は完全一致のみ、という非対称が今回の穴である。

### 2.5 マッピング定義自体は正しい

Drive の実ファイル構成とマッピング定義は完全に整合している。

| | MASTER 登録 | 捨て問 | またがり | `*Assets.ts` の行数 | Drive 実枚数 |
|---|---|---|---|---|---|
| etheory | 42（問1〜46） | 4（問5,9,20,45） | 4（問13,35,40,46） | 46 = 42+4 | 50 = 46+4 |
| ecircuit | 52（問1〜58） | 6（問13,14,15,41,46,54） | 17 | 69 = 52+17 | 81（+奥付1は対象外） |

`問N` の N は MASTER の `number` と一致し、`-1` / `-2` は `sort` 0/1 に対応する。
つまり**マッピングの中身を作り直す必要はなく、キーの表現だけが古い**。

## 3. 利用者から見えていた症状

`hasKnownAsset()` は `ASSET_MAP` から判定するため、電子理論・電子回路の問題にも
「問題を見る」ボタンは表示される。しかし `fetchAssets()` は0件を返すので、
`ProblemViewer` が
「この問題の画像はまだ取り込まれていません。ヘッダーの「取り込み」から画像を登録してください。」
を出す。案内どおり取り込みを試しても §2.4 の分岐で何も起きない、という手詰まりになっていた。

## 4. 影響範囲

- 電子理論 42問・電子回路 52問（理論の約 22%）の画像が閲覧できない。
- 同じ理由で、**既存7章の再取り込み・差し替えも現状の Drive ファイルからは不可能**。
  Storage 上の既存357枚は旧名で保存済みのため、閲覧自体には影響しない。

## 5. 対処の選択肢（未実施・要判断）

1. **`ASSET_MAP` のキーを `問N.png` 形式へ移行する**（推奨）
   `src/data/*Assets.ts` を現行 Drive の命名に合わせて再生成する。
   ただしキーは章をまたいで一意でなくなる（`問1.png` が9章に存在）ため、
   `ASSET_MAP` を「章コード → ファイル名 → 参照」の2段構造にするか、
   取り込み時に章を選ばせる必要がある。`storagePath()` の章分割は維持できる。
2. **分野別モードにも `問N` 逆引きのフォールバックを入れる**
   年度別と同じ考え方。ただし章の指定が要るため、結局1と同じ「章の選択」が前提になる。
3. **Drive 側を旧命名へ戻す**
   コード変更は不要だが、`問N` 命名のほうが人間には可読で、
   MASTER の `number` と直接対応するため、将来的にも壊れにくいのは 1/2 側である。

いずれの案でも `docs/problem-data-integration.md` §5.1 の状態欄
（現状「マッピング確定」としか書かれておらず、投入済みかどうかが読み取れない）を
「マッピング確定／投入済み」「マッピング確定／未投入」に分けて記録すべきである。
