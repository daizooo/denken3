# 電子理論・電子回路の取り込みが完了していなかった原因と修正

調査日: 2026-08-31 / 対象: `etheory`（電子理論）・`ecircuit`（電子回路）

## 1. 結論（根本原因）

原因は2つあり、**両方が同時に塞がっていた**ために2章がまるごと残った。

### (A) 分野別の取り込み経路（一括投入スクリプト）がリポジトリに残っていなかった

`docs/problem-data-integration.md` §5-2 は、分野別の投入を
**移行スクリプト（Node、章フォルダ数十枚を一括で put ＋ insert）** の仕事と定めている。
分野別は章単位のバッチ作業で、アプリの取り込みパネルへ1枚ずつ落とす運用ではない。

ところがそのスクリプトは「**1回限りの取り込み用**」として残されず、
**新しい章を投入しようとした時点で手段が存在しない**状態になっていた。
①〜⑦が入っていて⑧⑨が入っていないのは、⑧⑨がその手段を失った後に来た2章だからである。

### (B) もう一方の経路（取り込みパネル）は完全一致でしか引けなかった

同じ不具合は年度別取り込みで一度発生し、**PR #56（`02f3b2b` / 2026-07-25）で修正済み**である。

> 年度別取り込み: ファイル名の「問N」表記からも問題を逆引き
> GoogleDriveからそのまま持ってきた電験王キャプチャの元ファイル名は imageFile と
> 完全一致しないため**全件スキップされていた**。

このとき修正されたのは `handlePaperFiles`（年度別）だけで、`handleFiles`（分野別）は
`ASSET_MAP[f.name]` の完全一致のままだった。つまり **「取り込み元のファイル名は変わりうる」
という既知の前提に対して、2つある取り込み経路の片方しか対応していなかった**。

その結果、(A) で本来の経路を失ったあと、残った唯一の経路（パネル）も
現行の `問N.png` 命名を1件も受け付けない、という詰みになっていた。

### なぜこの2章だけなのか

章は番号順（①直流回路 → ⑨電子回路）に取り込まれており、**⑦電気計測まで終わった時点で
取り込み元のファイル名が変わった**。時系列は以下のとおり。

| 日時 | 出来事 |
|---|---|
| 2026-07-21 | ①直流回路を取り込み（`newIMG_0283`〜） |
| 2026-07-22 | ②単相交流・④過渡現象・③三相交流・⑤静電気・⑥電磁気を取り込み |
| 2026-07-24 08:00 / 23:38 | ⑦電気計測を取り込み（`newIMG_0478`〜`0537`）＝**旧命名での最後の取り込み** |
| 2026-07-25 00:31 | PR #56。年度別の「完全一致で全件スキップ」を修正（**分野別は未修正のまま**） |
| （時期不明） | 一括投入スクリプトが手元から失われる（リポジトリには元から無い） |
| 2026-08-03 07:52 | GoogleDrive の章フォルダ一式が `問N.png` 形式で作り直される |
| それ以降 | ⑧電子理論・⑨電子回路は、一括経路が無く、パネルは完全一致のみで1件もヒットしない |

①〜⑦は「命名が変わる前に取り込みが済んでいた」から無事だっただけで、
**この2章に固有の欠陥があったわけではない**。同じ理由で、既存7章の再取り込みも
現行の Drive ファイルからは不可能な状態だった（Storage 上の既存357枚は旧名で
保存済みのため、閲覧自体には影響しない）。

### なぜ失敗に気づけなかったのか

一致0件のとき、分野別ハンドラは例外もエラーも出さずこう表示して終了していた。

```
対象の画像が見つかりませんでした（50件は未登録/捨て問のためスキップ）。
```

「捨て問だからスキップ」という**正常系に読める文面**であり、かつ取り込み済みかどうかを
確認する手段がパネル上に無かった（年度別には ✅/⬜ の一覧があるが、分野別には無かった）。
失敗が失敗として見えないことが、放置が続いた第2の原因である。

### 2.2 Storage（`denken-problems`）

### 2.3 GoogleDrive 側のファイル名

親フォルダ配下の章フォルダ（⓪電気の基本〜⑨電子回路）は**全章とも `問N.png` 形式**。
`newIMG` で Drive 全体を検索してヒット **0件**（旧命名のファイルは1つも残っていない）。

- ⑧電子理論: `問1.png`〜`問46.png`、またがりは `問13-1.png` / `問13-2.png`（計50枚）
- ⑨電子回路: `問1.png`〜`問58.png`、またがりは `問9-1.png` / `問9-2.png`（計81枚）
- ⑦電気計測: `問1.png`〜`問51.png`（`問31,32.png` = 2問同居）

同一コーパスの改名であることは枚数で裏が取れる。例えば電気計測は Drive 実枚数59枚で、
`docs/problem-data-integration.md` の「59枚実読」と一致する。

### 2.4 マッピング定義自体は正しい

| | MASTER 登録 | 捨て問 | またがり | `*Assets.ts` の行数 | Drive 実枚数 |
|---|---|---|---|---|---|
| etheory | 42（問1〜46） | 4（問5,9,20,45） | 4（問13,35,40,46） | 46 = 42+4 | 50 = 46+4 |
| ecircuit | 52（問1〜58） | 6（問13,14,15,41,46,54） | 17 | 69 = 52+17 | 81（+奥付1は Drive に無し） |

**マッピングを作り直す必要はなく、引き方だけが古かった。**

## 3. 修正内容

### 3.1 取り込み経路そのものが残っていなかった（本丸）

`docs/problem-data-integration.md` §5-2 は、分野別の投入を
**移行スクリプト（Node、章フォルダ数十枚を一括で put ＋ insert）** の仕事と定めている。
分野別はアプリの取り込みパネルへ1枚ずつ落とす運用ではない。

ところがそのスクリプトは「1回限りの取り込み用」としてリポジトリに残されず、
**章を追加しようとするたびに手段が無い**状態になっていた。
①〜⑦が入っていて⑧⑨が入っていないのは、その手段が失われた後に来た2章だからである。

そこで取り込み経路を常設した。

**`scripts/import-bunya.mjs`（新規）／ `npm run import-bunya`**

```
# まず中身を確認（Supabaseへ一切触らない。認証情報も不要）
npm run import-bunya -- --chapter etheory --dir ./⑧電子理論 --dry-run

# 実投入
SUPABASE_URL=... SUPABASE_SERVICE_ROLE_KEY=... \
  npm run import-bunya -- --chapter etheory --dir ./⑧電子理論
```

- 章フォルダを列挙し、各ファイルを `src/data/{chapter}Assets.ts` の正規名へ解決する。
- `denken-problems/{uid}/theory/{chapter}/{正規名}` へ put し、`denken_question_assets` へ upsert
  （`region` / `sort` / 各 pct はマッピングの値をそのまま入れる）。冪等なので再実行してよい。
- 捨て問・奥付・章違い・想定外の命名はスキップし、最後に理由付きで一覧する。
- **マッピングにあるのにフォルダで見つからない画像があれば警告して終了コード1**。
  章を取り違えて実行しても取り込みが静かに欠けない。
- 章コードは `src/data/*Assets.ts` の存在から引くので、章を足してもスクリプトの修正は不要。
- 認証情報の扱いは既存スクリプト（`peek-asset` / `detect-pcts`）と同じ
  `assertSupabaseCredentials()` に揃えた。service key はリポジトリに置かない。

### 3.2 ファイル名の解決規則（`src/lib/bunyaFilename.ts`・新規）

| 入力 | 解決先 |
|---|---|
| `newIMG_0550.png` | 完全一致（既存7章の再取り込み互換） |
| `問13.png` / `問13-1.png` | その章の問13・`sort 0` の正規ファイル名 |
| `問13-2.png` | 問13の解答続きページ・`sort 1` |
| `問31,32.png` | 2問同居画像（先頭番号で解決） |
| 捨て問・奥付・章違い・想定外 | `undefined`（スキップ） |

`問N` は章ローカルで章をまたぐと一意でない（`問1.png` は9章すべてに存在する）ため、
必ず章コードとその章のマッピングを伴って引く。

このファイルは**型以外を import しない**ため、Node の型剥がしでスクリプトからそのまま読める
（tsconfig の `erasableSyntaxOnly` と対）。アプリとスクリプトで解決規則が2箇所に分かれない。

### 3.3 取り込みパネル（`src/components/ImportPanel.tsx`）

パネルは1枚〜数枚の追加・やり直し用だが、同じ穴があるので同じ解決規則へ寄せた。

- 分野別モードに**章の選択**を追加（年度別の回選択と同じ形）。各章に ✅/⬜ と
  保存枚数・想定枚数を表示し、**未取り込みの章がパネル上で分かる**ようにした。
- 保存先ファイル名を正規名へ統一（年度別が `imageFile` へ統一するのと同じ）。
- 一致0件のメッセージを、正常系に読めない診断的な内容へ変更した。

### 3.4 `src/lib/assets.ts`

`ASSET_MAP` を章コード別の `CHAPTER_ASSET_MAPS` から組み立てる形に変更
（統合マップの中身は従来と同一。`hasKnownAsset` などの既存利用に影響なし）。

## 4. 検証

### 4.1 解決規則

```
1) 完全一致(既存互換): 全9章 472 件 OK
2) 2問同居: 問31,32.png と 問32.png がともに newIMG_0511.png（2問）へ解決 OK
3) 解答またがり: 問13-2.png → newIMG_0551.png（etheory_13 / sort 1）OK
4) 章違い・範囲外・未知命名は解決しない OK
```

### 4.2 取り込みスクリプト（現行Driveと同じファイル名構成でドライラン）

```
章: etheory   画像 50 枚 → 取り込み対象 46 件 / スキップ 4 件（マッピング全体は 46 件）  exit=0
              スキップ: 問5.png 問9.png 問20.png 問45.png（＝捨て問4件と一致）
章: ecircuit  画像 81 枚 → 取り込み対象 69 件 / スキップ 12 件（マッピング全体は 69 件） exit=0
              スキップ: 捨て問6問×2枚
```

- 取り込み対象数が**マッピングの全件数と一致**し、「見つからなかった画像」は0件。
- 旧命名（`newIMG_*`）だけのフォルダも 50/50 で通る（既存章の再取り込み互換）。
- 章を取り違えて実行すると「見つからなかった画像 28 件」と警告し終了コード1で止まる。
- 未知の章コードは指定可能な章一覧を出して停止する。

`npm run build` 通過・lint エラー0。

## 5. 残作業

画像の実投入は、**service role キーを持つ手元の環境で**下記を実行するだけ。
service key はリポジトリにも外部にも出さない方針（§5 の但し書き）のため、ここは手元作業になる。

```
# ⑧電子理論・⑨電子回路 を GoogleDrive からローカルへ落としてから
npm run import-bunya -- --chapter etheory  --dir ./⑧電子理論  --dry-run   # 46/46 になることを確認
npm run import-bunya -- --chapter ecircuit --dir ./⑨電子回路 --dry-run   # 69/69 になることを確認

# .env に SUPABASE_URL / SUPABASE_SERVICE_ROLE_KEY がある状態で --dry-run を外して実行
npm run import-bunya -- --chapter etheory  --dir ./⑧電子理論
npm run import-bunya -- --chapter ecircuit --dir ./⑨電子回路
```

投入後に `npm run peek etheory_1 ecircuit_1` で署名付きURLを開いて表示を確認し、
`docs/problem-data-integration.md` §5.1 の状態欄を「投入済み」へ更新する。
